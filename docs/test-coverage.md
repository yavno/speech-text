# What the tests cover

What each test file holds, for finding the test beside the code you change. The test
names and their assertions are the record; this list is a guide to them and falls behind.
How to run them and the rules they follow are in `AGENTS.md` › Tests and
[development.md](development.md#tests).

`xcodebuild test -project SpeechText/SpeechText.xcodeproj -scheme SpeechText -destination 'platform=macOS'` runs the `SpeechTextTests` unit-test bundle (sources in `SpeechText/SpeechTextTests/`). CI also records its line coverage in the job summary (`scripts/coverage-summary.sh`, informational) and lints the Swift lines a pull request changes with `scripts/lint-swift.sh` (`.swift-format`: a filtered set of semantic rules, never a reformat — CONTRIBUTING.md › Formatting). CI adds `SPT_WARNINGS_AS_ERRORS=YES`, which the project maps onto `SWIFT_TREAT_WARNINGS_AS_ERRORS` for our four targets only, so a compiler warning in our code fails it (docs/development.md › Compiler warnings); pass the same flag to see what CI will say. It is **standalone — no `TEST_HOST`, no `@testable import` of the app**: the app is an LSUIElement agent that prompts for microphone access at launch, so hosting tests inside it would hang a headless run. Instead the test target compiles no app source: the logic it tests lives in a local Swift package, `Packages/SpeechTextCore` — every file under `Sources/SpeechTextCore/` (the settings, catalogues, transcribers, the upload and streaming sessions, History, and the pure logic of delivery, shortcuts, text and usage; the bullets below say which) and, as a product of its own, `Sources/ChatTemplates/` — which the app, the tests and the tool link: a file there needs no `project.pbxproj` edit, the app and the tool `import SpeechTextCore` and reach only what is `public`, and the tests `@testable import SpeechTextCore` — a module, not the app, so the bundle stays standalone. The consequence: **logic that test code needs goes in the package**, and so must anything a package file comes to depend on; the test target's Sources phase holds only its own files, and the `SpeechTextEvaluation` tool's only its own and the engine runtimes it runs (LocalSTTRuntime, LocalWhisperRuntime, LocalParakeetRuntime, VoiceActivityRuntime, LocalLlamaRuntime). What stays in `SpeechText/SpeechText/` is what the package may not hold: the views, `AppState`, `SpeechEngine`, the capture and the Apple recogniser, `PasteService`, the hotkeys, the engine runtimes, the stores, `LocalChatClient` / `LocalChatXPC` and `KeychainSecretStorage`. A package file must not reach into that graph, or the package stops closing; `import SwiftUI` there is refused by CI's *Core imports* check (`scripts/check-core-imports.sh`). It cannot `import WhisperKit`, `FluidAudio`, `Sparkle` or `llama` at all: the manifest declares no dependency, so such an import is a build error rather than a rule for review — which is why the local tier reaches both its engines through the `LocalSTT` registration box.

`scripts/vendor-watch/test_check.py` (Python, run by CI's *Vendor watch script* step) covers how that script reads the vendors' pages, from short copies of them: each deprecation table's dates, IDs and replacements (an escaped `|` in a cell, an Anthropic alias found by its dated snapshot), a current model on the page, a deprecated one whose date moved, an Active model past its earliest retirement, a per-account "gone" confirmed by the page, a page with no table it knows or a known table with no rows not checked; a changelog's new lines (a moved line not new, a longer ID not taken for a catalogue one), the first run storing a baseline and two copies kept; and the JSON findings.

`scripts/vendor-watch/test_file_issues.py` covers which finding `file_issues.py` files: a new one opens an issue, the same one on an open issue stays quiet, a changed one comments once, a closed issue with the same finding stays closed and a changed one opens a new issue linking it, `wontfix` and `vendor-watch:ignore` silence a key, findings with one key make one issue, new repositories only listed, no more than ten new issues a run, an issue without the marker never matched; an unconfirmed per-account "gone" titled so, a confirmed one linking the page, and vendor text that can neither mention anyone nor carry HTML.
`APIKeyStoreTests` covers the store's launch rules against an isolated `suiteName` and a keychain in memory: a key moved in and deleted from every domain, the newest pre-rename domain filling a missing one, a pre-rename copy never replacing the keychain's, a current-domain key (a ⌘R build's) replacing it, a failed write, a read-back mismatch or an unreadable keychain keeping every copy, a failed save never falling back to a plist, and a build without the keychain adopting from the chain and not resurrecting a key the user cleared. Tests never touch `UserDefaults` or a real keychain
— the user's settings live in the `app.speech-text.SpeechText` domain, and a build without the profile keeps the API keys there
— so anything that reads defaults (`RecordingConfiguration.current()`, `PromptPresetStore.load()`) is bypassed by constructing values directly.
