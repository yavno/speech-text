# How SpeechText behaves, and why

The decisions behind the app's behaviour, most of them learned from a measurement or a
bug. Read the entry for what you are about to change; break one only on purpose, and
rewrite its entry in the same pull request. [architecture.md](architecture.md) is the map
of the code; `AGENTS.md` has the rules for working in it.

## The renames

The app was called **VoicePeter** until the 2026 rebrand, and the rebrand itself first shipped the name misspelled (**SpeachText**). Each step moved the bundle identifier (`com.voicepeter.app` → `com.speachtext.app` → `com.speechtext.app` → `app.speech-text.SpeechText`, the last one the project's own domain, speech-text.app, reversed — taken before the first public release, so that only the maintainer paid for it), and macOS keys microphone, speech-recognition and accessibility grants to it, so each change re-asks for all three. Two one-shot migrations keep the rest from reading as a factory reset, and both walk a *chain* of old names rather than a single one: `TranscriptionHistory.adoptPreRenameStore()` moves the newest surviving Application Support folder (`SpeachText/`, else `VoicePeter/`) to `SpeechText/` — named for the product, not the bundle identifier, so the last move left it where it was — and `adoptPreRenameDefaults()` (Settings.swift) copies `SettingsKeys.portable` out of `com.speechtext.app`, then `com.speachtext.app`, then `com.voicepeter.app` — shortcuts and prompt presets included — newest domain first, never overwriting a key already present. The API keys are not in `portable`: `APIKeyStore.open` walks the same chain for them, and in a keychain build deletes every copy it moves. Their keychain group is fixed at `TEAMID.app.speech-text.SpeechText` (`KEYCHAIN_GROUP_SUFFIX`, scripts/keychain-profile.sh) and must not follow a rename: a group that moved would hide every stored key, with the plain-text copies already gone. `hasRegisteredLaunchAtLogin` is deliberately left behind: it records a registration made under an *old* bundle identifier, and carrying it over would leave the renamed app convinced it is already a login item when it is not.

## Building, measuring, shipping

Open `SpeechText/SpeechText.xcodeproj` in Xcode and build (Cmd+B) / run (Cmd+R). Three Swift packages, all pinned in `project.xcworkspace/xcshareddata/swiftpm/Package.resolved`: WhisperKit (`argmaxinc/argmax-oss-swift`) and FluidAudio (`FluidInference/FluidAudio`) for the two local speech engines — and the voice activity detector — and Sparkle (`sparkle-project/Sparkle`) for updates — the file also pins `swift-argument-parser`, which one of them pulls in and the app never imports. A fourth, llama.cpp, is a local package (`Packages/LlamaBinary/`): a `binaryTarget` at ggml-org's prebuilt `llama.xcframework`, pinned by build and checksum, linked only by the SpeechTextLLM service and the `SpeechTextEvaluation` tool — never by the app. The app's own logic is a local package too, `Packages/SpeechTextCore`, which depends on nothing (see `AGENTS.md` › Tests). Everything else is Apple frameworks. See **Four dependencies, one file each** below. Their licences, and those of the code each carries inside it (WhisperKit's `NOTICES`, FluidAudio's `ThirdPartyLicenses/`), ship as `Resources/ThirdPartyNotices.txt`, opened by Settings › General › Acknowledgements and generated by `scripts/third-party-notices.sh` from the pinned checkouts — rerun it after any package change; `ThirdPartyNoticesTests` fails while the file names a version `Package.resolved` no longer pins (`swift-argument-parser`, which is not linked into the app, is left out).

`scripts/e2e.sh` runs the app itself with no person: a debug build stamped `app.speech-text.SpeechText.e2e` records from corpus clips, its real global shortcuts are posted as key events (`scripts/e2e/keys.swift`), the result is read back from TextEdit and Script Editor with AppleScript, and `scripts/e2e/check.py` judges it structurally — pasted once, into the document opened, a cancel leaving it empty, an edit replacing the selection; WER is shown, never judged. It quits the installed app for the run and reopens it, needs Accessibility for the e2e build and for the app running it, and never runs in CI — `docs/e2e.md`.

`scripts/check-vendor-models.sh` compares the catalogues, exported by `SpeechTextEvaluation --export-catalogue`, with what OpenAI, Groq, Anthropic and ElevenLabs serve now, newer FluidAudio and WhisperKit releases, and the local models' Hugging Face repositories. It reports models gone, shutdowns announced, price drift and language lists changed at their source, reads the vendors' deprecation pages and the new lines of their changelogs, with keys from `~/.config/speech-text/test-keys.env` or the environment. It never runs in CI; the vendor watch workflow runs it every day and files what it finds as `model-lifecycle` issues, with no language model anywhere, and a tag is released only after a green run on `main` within seven days (`docs/vendor-watch.md`, `docs/releasing.md`).

`scripts/evaluate-rewrite.sh` measures AI Rewrite: the text fixtures in `SpeechTextTests/Rewrite/rewrite-fixtures.json` through the app's own prompt, client (`LLMConfiguration.makeChatClient(model:apiKey:)`) and parser on cloud and local chat models (`SpeechTextEvaluation --rewrite`), every reply held to `RewriteChecks` — text checks that hold whatever the prompt, apart from the mode a prompt variant expects — with an LLM judge only when `--judge` is given. The checks are held to the fixtures' hand-written examples first (`--self-check`). Runs go to `SPEECHTEXT_RUNS`, outside the repository; a prompt change is compared with the baseline before it (`docs/rewrite-evaluation.md`). It never runs in CI.

`scripts/rebuild.sh` (a plain shell script the user runs themselves) builds Release, installs to `/Applications/SpeechText.app`, stops every running instance under every name the app has shipped as, and relaunches it; its flags (`--status`, `--rollback`, `--tag X.Y.Z`, …) are described in `docs/rebuild.md`.

Target: macOS (native Swift/SwiftUI). The app runs as a menu bar agent (`LSUIElement = true`) and opens no window at launch; by default it keeps a Dock icon all the time, and can be set to show one only while the main window, Settings or another ordinary window is open, or never (`DockIconMode`). Every target of ours builds in the Swift 6 language mode (`SWIFT_VERSION = 6.0`; `.swiftLanguageMode(.v6)` and `swift-tools-version:6.4` in the package), so the project takes Xcode 27.1 or later, and with no warning in our own code — a new one is fixed, not left. Isolation is written out per type, with no default main-actor isolation and no `NonisolatedNonsendingByDefault`; a closure an API calls off main is written `@Sendable`, or the runtime stops the app when it runs there — docs/development.md › Concurrency.

Both configurations build with the **hardened runtime**, and `SpeechText.entitlements` declares every protected resource it gates (audio input, and Apple Events for the AppleScript fallback that re-activates the target app) — a feature that touches a new one needs its entitlement there, or it fails only in signed builds. The keychain group is the exception: its entitlements are *restricted*, so they never go in that file — `scripts/keychain-profile.sh` adds them, with the Developer ID provisioning profile, only to a build whose team, app and certificate the profile authorises (see **API keys live in the keychain when the build can reach it**). Releases are Developer ID–signed, notarized disk images made by `scripts/package-release.sh`, whose window (the app, a drawn arrow, Applications, in the setup window's style) is laid out by `dmgbuild` from `scripts/dmg/` — a build-time Python tool, pinned by hash and installed into a throwaway venv, that ships nothing in the app; pushing a `vX.Y.Z` tag runs `.github/workflows/release.yml`, which opens a *draft* GitHub release. Credentials live only in repository secrets. `docs/releasing.md` has the one-time setup — including why the signing team must be chosen before the first public release: the team ID is part of the identity macOS keys every permission grant to.

## Recording modes

- **Inline recording** — Triggered by global hotkey (default: `Ctrl+Shift+Q`). Shows a small floating overlay (`RecordingOverlay.swift`) in the bottom-right corner, or wherever the user dragged it. With a tier that reports text while the user speaks — a realtime model, or Apple's on-device recogniser (`RecordingConfiguration.hasLiveText`) — the overlay shows the transcript as it is built and corrected. In every tier the text is pasted once, at the stop — see **Nothing reaches another app before the stop**. On stop, transcribed text is pasted at the cursor in the app in front at the stop via `PasteService` — see **The paste goes where the dictation ended** — and the overlay stays up a second more (`beginOverlayConfirmation` / `confirmOverlay`, `confirmationSeconds` = 1 s, then a fade) saying "✓ Pasted into Slack" on its transcript glass — opened for it whatever the tier — and no longer the recording's: ⎋ is let go, its ✕ only closes it, and the next dictation replaces it; a paste that went to the Record Window, or a fallback with a notice of its own, takes it down instead. A trailing space is added by `AppState.deliver` — every path upstream trims, and without it a dictation continued into the same field starts glued to the last one. It is added there, at the paste, so History and the span layer keep the transcript as it was recognised, and before the trace is written so a recorded dictation replays into the text that really went out (`DictationReplay.FakeApp.paste` mirrors it). Falls back to opening the Record Window if accessibility permission is missing or there is no app to paste into — or, with one already open, to adding the text after what it holds (`TextInsertionHandler.append`, one undoable step): an open Record Window is never closed and replaced by a fallback or by the menu's Record Window item, which only brings it forward, since its text lives nowhere else and a recording may be running in it.
- **Switching mode, and holding to talk** — during an inline or AI dictation the *other* mode's shortcut switches it over (the overlay's tint follows) and its own shortcut stops it. Nothing has been pasted before the stop, so a switch either way only changes what the stop does, and is never refused: plain → AI rewrites the whole dictation, AI → plain pastes it as it was said. `FocusContext` is read at the stop, once the mode can no longer change, and only for an AI dictation. With **Hold to talk** (`holdToTalk`) a held shortcut records until it is let go and a lone tap cancels (a tap that latched the recording left an overlay listening that no one asked for) — read retroactively, as the Edit shortcut reads its own, because a double tap locks the dictation on hands-free until the next press; while the first shortcut is held, every tap of the other flips the mode, so a switch to AI can be taken back. A press of the held shortcut itself means its release was missed, and follows the press table. The owner stays the shortcut that started the dictation even after a switch: letting it go stops the recording while the other is still held (a finger roll from Q to A reads as a stop — kept at the owner's call, since handing the dictation to the last key would make a tap of it a stop and break the flip back). **No cancel is silent**: every cancel of a dictation carries a `DictationCancelReason` (a shortcut while starting or busy, a lone tap, a release before the microphone opened, ⎋, ✕, the menu) and `AppState.cancelInlineFlow` shows a "Dictation canceled" notice for it — one cancelled during the AI rewrite says the dictation is in History, where the stop already wrote it. While a dictation is transcribed or rewritten the menu's two recording items read "Cancel Dictation", retitled whenever the menu opens (`menuNeedsUpdate`), since the phase moves on by itself. **Only the letter has to stay down**: Carbon reports a hotkey's release when its *key* comes up, whatever the modifiers do, so once a hold recording has started ⌃⇧ may be let go — nothing is typed while Q is held, clicks are ordinary and ⌘Tab works — and letting go of Q stops it (measured by the owner on 2026-09-27; a bare A then types "a", only ⌃⇧A switches, and that is kept). Nothing in the gesture changed for it; the app *says* so. `HeldShortcuts` (HotkeyManager.swift) records which shortcut's key is down from Carbon's press/release, and every place that draws a shortcut's keys does it live through `LiveShortcutKeycaps` (OnboardingChrome.swift): with hold to talk, once the letter is down the modifier caps turn *no longer needed* (`KeycapState.notNeeded` — faded, dashed) and the letter gets a ring — setup's Try it, Settings' shortcut rows and the hold tip; Settings › Dictation › Recording picks the mode with two segments, *Press to toggle* and *Hold to talk*, in words only (`RecordingModePicker`), and under them loops the chosen mode's gestures key by key (`GestureDemoList`, from `HoldTip.demoFrame` — a modifier is drawn down while it is, and *no longer needed* once let go with the letter still down). The **hold tip** is a small non-clicking panel beside the overlay (`HoldTipPanel`, following it as the transcript grows) for the first hold recordings: "You can let go of ⌃⇧", then "Just Q — that's it" once they are. `HoldTip` (DictationHotkeys.swift, pure, in SpeechTextCore) decides it from `holdTipFollowedCount`: shown until it has been *followed* (modifiers up, letter down) `lessons` = 3 times, then once the switch hint ("While holding Q, press ⌃⇧A") when there is another mode to switch to, then never. `AppState` polls the modifiers at 20 Hz only while a hold recording's letter is down (`beginHoldTip` / `endHoldTip`), shows the panel only after `tapThreshold` so a cancelling tap does not flash it, and never during setup, whose Try it step is the practice instead ("Now let go of ⌃⇧" → "✓ Just Q"). The Edit shortcut's hold gets the same tip, without the switch hint.
- **AI recording** — Triggered by global hotkey (default: `Ctrl+Shift+A`). With no AI provider configured the shortcut is simply a second dictation shortcut (`AppState.effectiveKey`), rather than a dictation that ends in "AI processing skipped" every time. Same flow as inline recording, but before pasting, the transcription is sent to an LLM by `TextRefinementService`. The dictation itself is the prompt: the model picks the best-matching prompt preset from `whenToUse` descriptions, applies that preset's instructions, and returns only the resulting text. The model is also told which app, window and field the text is for (`FocusContext`, read at the stop from the app the text is going to), so an unstyled dictation comes out as a chat message in Slack and a letter in Mail. The overlay stays up (tinted purple, with a sparkles badge) while the LLM works. Any LLM failure or refusal falls back to pasting the raw transcript, so a dictation is never lost. Nothing is pasted while the user speaks — the raw text is on the overlay only — so the rewrite is the one write.
- **Edit selection** — Triggered by global hotkey (default: `Ctrl+Shift+E`). Rewrites the text selected in the app in front: `PasteService.readSelection` reads it on the first press and again when the instruction ends — the second read is what gets rewritten — (through AX in Tier A, with the range; with a ⌘C and the clipboard put back otherwise), the microphone records an optional spoken instruction, and `TextRefinementService.edit` sends `<selected_text>` + `<instruction>` (+ `<context>`, + the Dictionary's `<vocabulary>`) under its own system prompt — with no instruction it polishes; with one, the presets are a vocabulary the instruction may name. The overlay is *filled* violet with the pencil-and-sparkle `EditGlyph` (AI dictation is only outlined), and the instruction is never pasted; a rewrite pasted over the selection leaves the overlay saying "✓ Selection replaced" for a second, as a dictation's says where it went. See **An edit cuts the selection when the instruction ends, and puts it back on any failure** for the write.
- **Record Window** — Triggered by global hotkey (default: `Ctrl+Shift+W`). Opens `DirectRecordingPanel.swift`, a floating panel that auto-starts recording. The transport knob starts, pauses and resumes; the dot matrix along the bottom shows the level while recording and a sweeping comet while a provider is working. Transcribed segments land in an editable text column; while the column is still empty the transcript in progress is printed on the glass, with what has settled drawn brighter than the partial the recogniser may still take back. The button rail on the right inserts at the cursor or copies. The hotkey toggles recording when the panel is already open; ⎋ or ⌘W closes it, as does the ✕ that sits below the button rail, outside its recess. The rail's ✨ button turns on LLM processing: each time a segment finishes transcribing, *that segment* goes through `TextRefinementService` and its result is written over it — where `FinalizePass.plan` finds it untouched, as one undoable edit (⌘Z, which the panel wires by hand since an agent has no Edit menu). Sending the whole text area instead let a preset picked for the latest segment rewrite everything before it: a shopping list turned 129 characters into 27. Turning ✨ on with text already present refines the whole text once. Either way `TextRefinementService.isCollapse` refuses a result under half its input's length — kept as dictated, with a notice and a History note — unless the pass was a single segment routed to a summarising preset (Structured). The phosphor turns violet for as long as it is on.

## Key patterns

- **`@Observable` macro** — Used for every observable model (`SpeechEngine`, `AppState`, `HotkeyManager`, `TranscriptionHistory` and `DebugLog`, and e.g. `APIKeyStore`, `LocalModelStore`, `HistoryRetry`, `OnboardingModel`, `OverlayLayout`) — the Swift Observation framework, not Combine.
- **UserDefaults via `@AppStorage`** — All settings stored in standard UserDefaults, except the API keys (below). Keys defined in `SettingsKeys` enum.
- **API keys live in the keychain when the build can reach it** — a plist in `~/Library/Preferences` is read silently by any process running as the user, and these are billing credentials. A build signed with the Developer ID provisioning profile (releases; `rebuild.sh` with `~/.config/speech-text/SpeechText_Developer_ID.provisionprofile`) keeps them in the *data-protection* keychain, in the group `TEAMID.app.speech-text.SpeechText`, which no other team's code can name — not the file-based login keychain, which asks the user and is one click from yes, and prompts on every teamless rebuild. A build without the profile gets `errSecMissingEntitlement` from that keychain, so it keeps them in UserDefaults as before. The mode is read from the app's own signature, never inferred from a failed call, so a transient error cannot put a release's keys back in a plist. The group does not follow the bundle identifier (see the rename paragraph at the top). In keychain mode `open` moves each key it finds — the current domain first, since a ⌘R build shares it and anything there is newer than the keychain; otherwise the pre-rename chain, which only fills a missing key — writes it, reads it back, and only then deletes it from all four domains; any failure keeps every copy. A failed save from Settings is kept for the session and logged, never written to a plist instead. The cost: a change of Apple team makes the items unreachable (keys re-entered), a new Mac starts without them (`ThisDeviceOnly`), and a ⌘R build cannot see what a signed build moved. The restricted entitlements are never in the tracked entitlements file, and `package-release.sh` refuses a distributable image without them — see docs/development.md › API keys.
- **`NSPanel` subclasses** — Floating panels use `.nonactivatingPanel` style so they don't steal focus from the user's active app.
- **Two skins, same capabilities** — `AppSkin` picks the chrome, never the feature set. `RecordingOverlayView` and `DirectRecordingPanelView` each keep both variants in one file, and the record window's buttons come from a single `railActions` list that both chassis render — so a button cannot exist in one skin and be quietly missing from the other. Closing the window is the one exception: techno draws its own ✕ below the rail, because minimal already has the system titlebar's close button and a second one beside it would be nonsense. Adding a third skin is a case in `AppSkin`, its two panel sizes, and a `body` branch in those two views. VoiceOver names come from the same place: `PlasticButton`, `MinimalIconButton` and `TransportKnob` take a required `label` (a short name — the `.help` sentence is already read as the hint) and an optional `value` for a state, a `RailAction` carries both, the transport's state is one `transportState` both chassis read, and the overlay's meter is one element saying the mode and what it is doing, in either skin; pictures of the controls (Settings' skin previews, setup's demo strip, Home's intro card) are hidden from it.
- **Neutral is the default, a tint is opt-in** — `AccentColor.neutral` (an empty stored value) paints the level meter in `.primary` and the transport red, which is what the app has always looked like. An accent applied to *everything* turns a quiet sliver of glass into a coloured object, so the user has to ask for it. `Semantic.confirmation` keeps the copy/paste/send flash green regardless.
- **An accent on minimal, a whole display palette on techno** — techno's every colour was matched against the design render, so `AppSkin.supportsAccent` keeps the minimal accent out of it. Its colour is a *phosphor colour* instead (`technoPhosphor`), always a whole `TechnoPalette` — glass, recess, dots, text, peak, and a hue turn for the shell's green-printed texture — because amber dots on the design's green glass look like a fault. Four recommended sets are matched by hand (`TechnoPhosphor`, DesignKit.swift: green — the design, and the default — amber, cyan, white); any other colour from the colour well is stored as `#RRGGBB` and its set derived in the design's proportions (`TechnoPalette(deriving:)`: glass at the dot's hue, 14% brightness, 70% of its saturation; dots kept at least 55% bright). The surfaces read it from `\.technoPalette`, which each root view (`RecordingOverlayView`, `DirectRecordingPanelView`, `SkinPreview`) sets from the stored key; `TechnoSkin`'s own statics stay the design's green, because the setup window borrows them. No recommended set is violet or red: AI mode on techno recolours only the phosphor, and red on the glass is the error text. A colour of the user's own near AI's violet is allowed, with a warning under the row (`isCloseToAI`). The Record Window's copy/paste flash stays the design green whatever the display is. AI mode's violet (`Semantic.ai`) is fixed in both skins: if it followed the accent, a user who picked violet would lose the one signal that tells a rewritten dictation from a plain one.
- **The window chrome is part of the skin** — minimal wears an ordinary titled `NSPanel`, so its rounded corners, the glass behind it (`minimalGlass`) and the close button all come from the system; reimplementing those only produces a worse copy. Techno is borderless because it draws its own moulded shell, and a titlebar there would sit on top of the moulding and swallow clicks meant for the knob. `DirectRecordingPanelWindow.applySkin()` swaps the `styleMask`.
- **Skin changes resize the window by hand** — the hosted SwiftUI reflows through `@AppStorage`, but the `NSPanel` around it does not, and the two skins are different sizes. Both panel classes observe `.skinDidChange`: `DirectRecordingPanelWindow` calls `setContentSize`, and `RecordingOverlayPanel` recomputes its `OverlayGeometry` for the new skin and re-places itself at the saved spot, which sets its frame.
- **One skin, two surfaces** — within the techno skin, the inline overlay and the record window are the same device. Every colour, radius and dot pitch lives in `TechnoSkin` (DesignKit.swift), so neither surface can drift from the other or from the Figma file.
- **Traced shapes keep their path data** — `LCDScreenShape` stores the two `d` strings Figma exported and scales them onto whatever rect it is given, instead of a hand translation into `Path` calls. Re-exporting a tweaked vector is then a copy-paste. The two halves are `union`ed, not merely overlaid: they share an internal edge at the knob's waistline, and the inner shadow strokes the shape, so anything less would draw a seam across the glass.
- **The knob is drawn, not exported** — `TransportKnob` rebuilds the design's layer stack (bevel → outer disc → groove → cap → glyph) in SwiftUI because the app needs the knob in states the design never drew (recording, transcribing, AI, hover, pressed) and a bitmap can't take a different glyph or tint. Its shading was matched against the design render pixel by pixel; changing a gradient stop by feel will drift.
- **The bevel is a `.background`, not a ZStack layer** — it is larger than the knob, and a `ZStack` re-proposes its final size to flexible children, so putting it in the stack silently inflates the disc to match it.
- **The display has its own clock, and bounces in place** — `PixelWaveform` runs at a fixed 30Hz and samples `barLevels` on each tick, rather than advancing when the audio tap fires: Core Audio's callback rate varies, so anything driven from it speeds up and slows down. Every column is redrawn from the *current* loudness (the mean of the engine's per-segment heights, not the peak — one transient in any segment pins the peak to full height) times a hashed per-column jitter, so the grid jumps up and down like a hardware equaliser. The heights arrive already scaled to the voice by `LevelNormalizer`, so any microphone fills the glass; the display applies no gain of its own, and the synthetic voices in Home's intro card and setup's demo strip feed it heights directly. Columns ease towards their target (quicker up than down) instead of stepping onto it, the topmost dot fades in with the fraction of a row the column has grown into — eight rows are too coarse to move smoothly otherwise — and each lit dot carries a little hashed brightness variation, so the field reads as phosphor rather than as a chart. It deliberately does not scroll a history sideways: a track travelling across the glass reads as a progress bar rather than as a voice. The jitter is hashed from column and draw index instead of drawn from a random source, because a body re-evaluation has to reproduce the same grid; both directions are eased, the rise (`attack`, 0.45 of the gap per tick) about three times faster than the fall (`release`, 0.16), which is what keeps a syllable visible without the whole grid strobing.
- **Streaming rides alongside the audio file, never instead of it** — when a realtime model is selected (`scribe_v2_realtime` or `gpt-live-transcribe`), the fallback is *composition*: `StreamingRecognitionSession` wraps a `BatchRecognitionSession`, and the tap feeds Scribe's stream the 16 kHz Int16 bytes that `AudioBufferWriter.append` returns — one conversion serves both the file and the socket (OpenAI's wants 24 kHz; see **A stream that wants another rate**). The session keeps `committed` and `partial` apart (`RecognitionEvent.live(committed:partial:)`) and `SpeechEngine.liveText` is their join — so the Record Window's ghost text works exactly as it does for Apple. On pause/stop, `finish()` takes the stream's text; if the stream reported `failed`, or ended with nothing, the session clears the ghost text and hands over to the wrapped batch session, which uploads the same writer's file. History is written by the engine from the returned `RecognitionOutcome`, whichever half produced it. `RecordingConfiguration.batchModel` maps each realtime model ID to its vendor's upload model (`scribe_v2`, `gpt-transcribe`) for that fallback (and for History retries), because a realtime model does not exist behind the upload endpoint. Whether ElevenLabs or OpenAI shows live text is therefore a function of the stored model (`streams`), not of the provider enum.
- **OpenAI's stream is a different shape, and the differences are absorbed in the transcriber** — `gpt-live-transcribe` (checked against the live service 2026-09-21) runs *no* voice-activity detection: a fresh session defaults to `server_vad`, which the model rejects ("Turn detection is not supported for this transcription model"), so `encodeSessionUpdate` sends `turn_detection: null` — and nothing is ever committed on a pause and one item stays open, growing, until `finish()` sends `input_audio_buffer.commit`. Its transcripts arrive as *increments* (`conversation.item.input_audio_transcription.delta`), not as the cumulative restatements `TranscriptMerge` is written against, so `OpenAIRealtimeTranscriber` accumulates them per `item_id` and emits `.partial` as the whole segment so far; the `.completed` event's `transcript` is authoritative and replaces them (it ran a word or two ahead of the deltas every time). The adapter stays in the transcriber — `TranscriptMerge` is not taught about deltas. Two more sharp edges: a fresh session has `transcription: null`, so `session.updated` (not the `session.created` before it) is the "server is ready" signal the pre-session buffer waits for, and the commit is refused below 100 ms of audio, which is why the tail is padded with `STTTuning.streamCommitPaddingSeconds` of silence exactly as Scribe's is. An empty-commit error resumes the wait rather than failing the stream; the stop then falls back to the upload, which has the whole segment on disk. A stop that beats `session.updated` does not commit at once: `finish()` waits (`STTTuning.streamSessionReadyTimeoutSeconds`) for the flush of the held audio and commits behind it — a commit sent earlier reached an unconfigured session and was refused as empty — and past the bound fails the stream so the upload takes over.
- **A stream that wants another rate converts from the tap, not from the file** — the socket's audio format is the transcriber's to declare (`StreamingTranscriber.sampleRate`) and the caller's to satisfy; before OpenAI every transcriber happened to want the writer's 16 kHz, and `StreamingRecognitionSession` simply skipped a stream that did not. OpenAI's realtime session accepts *exactly* 24 kHz (16 kHz is "below minimum", 48 kHz "above maximum"), so the session now builds a second `PCMDownsampler` from the **native** tap buffer — 48 → 24 kHz in one step rather than 48 → 16 → 24 — and feeds the socket from that. ElevenLabs is untouched and still sends the writer's own bytes, so "one conversion serves both the file and the socket" still holds wherever it can. The converter is rebuilt when the tap's format changes, because a device restart hands it a new one mid-recording.
- **Nothing reaches another app before the stop** — Scribe's realtime VAD closes a sentence on a short pause ("…почнемо.") and re-states it a moment later once the user carries on ("…почнемо, потім"). The Record Window shows that correction because it owns its surface; text already pasted into another app cannot take it back, and Chromium, Electron and terminals could not be corrected at all. So every inline dictation, in every tier and mode, is built on the overlay and pasted once, at the stop. When the tier has live text (`RecordingConfiguration.hasLiveText` — a stream, or Apple's partials, which arrive as `.live` events like a stream's) `AppState` sets `showsLiveTranscript` and the overlay draws `spanLayer.stableText` + `segmentProvisionalText`; an upload tier shows the strip alone. There used to be a second path: committed spans pasted into the target app as they arrived, a tier probe at the start of every recording to decide how far that app could be corrected, a ledger of what landed, a finalizing pass that corrected it at the stop, and an opt-in AI draft replaced by the rewrite. Once streaming moved to the overlay only Apple's tier still reached it, and even that pasted once in practice, since it commits only at its 50 s rotation — so the path went, with `SpanIssuer`, `FinalizePass.decide`, `InsertionLedger.remainder`, `SpeechEngine.onFinalize` and the Tier B refusal of a switch to AI. A change that puts text into the target app before the stop has to answer the problem that removed it: text in a foreign document cannot be taken back. `DictationReplay` asserts on every replay that nothing was pasted before the stop. The Edit shortcut is not an exception: its instruction is never pasted.
- **A segment kept open too long is not trusted** — Scribe Realtime's VAD closes a segment only after 1.5 s of silence, so a paragraph read without one stays a single segment until the server cuts it by itself at about 36 s (ElevenLabs' commit-strategy guide, which advises committing every 20–30 s instead), and on the audio corpus a segment that ran that long ended in text nobody said — "Що ще?" fifteen times on the MacBook microphone in five runs of six, an invented schedule on the headset in two — and was pasted. This is the model's limit, not ours, and the answer is deliberately one guard rather than a fight with it. `StreamingRecognitionSession` measures each segment in audio sent (`OpenSegmentClock`, reset by every `.committed` and every new socket), and when the longest ran past `STTTuning.streamLongestTrustedSegmentSeconds` (30 s), `finish()` cancels the stream without waiting and the upload answers, as after an outage; the overlay showed the stream meanwhile. The limit comes from `RecordingConfiguration.longestTrustedStreamSegment`, set only for a realtime model whose server runs VAD — OpenAI's keeps one item open until the stop by design, and invented nothing on the corpus. Closing long segments from the client (`commit: true` mid-session at a measured pause) was built and measured first, and rejected at the owner's call: Scribe accepts such a commit and answers it like a VAD commit, but the reply often ends in a sentence that is not in the audio — the same words run to run, padded with silence or not, with later audio held back or not — and commits at comma-length pauses lost a whole segment on the MacBook microphone. 30 s rather than the 20 s tried first: a dictation with ordinary pauses (the clean `uk-hard-words`, one 25.7 s segment) stays on the stream and costs nothing extra. The cost: past 30 s the stop waits for the upload (about 4 s for a minute of speech) and the audio is paid twice (Usage › Overhead).
- **A dropped stream is reopened for the overlay, not for the text** — after a Wi-Fi drop the overlay froze where the link went, though the pasted text was right. `StreamingRecognitionSession` now asks `StreamReconnectPolicy` (NetworkFailure.swift, pure): a drop that `isReconnectable` — offline, a reset or stalled connection, a server that never started a session; never a refusal such as a rejected key or a quota — is retried after 0.5 / 1 / 2 / 3 / 5 / 5 / 5 / 5 s — about 26 s, longer than the outage itself, since macOS needs a few seconds after the Wi-Fi returns to join and answer DNS — up to three outages a segment. Each attempt is a *fresh transcriber* from the `reconnect` closure `makeRecognitionSession` passes (the same engine, from the same settings snapshot), because `connect` is once per instance — so the pre-session buffer, `sendLock`, the commit after `session.updated` and the echo filter all work for a reconnect exactly as for a first connection, and `StreamingTranscribers.swift` is untouched. The audio thread reads the transcriber to send to through a locked `TranscriberBox`, nil between a drop and its reconnect; each transcriber's events carry a generation, and a replaced one's late events are dropped; only a transcriber's first `.failed` counts, since a socket can report one drop from its receive loop and a send's completion at once, and the transcriber being replaced is cancelled — so one drop is one new socket and one outage. Before the swap the partial on screen is folded into the committed text — OpenAI's socket never commits before the stop, so otherwise everything said would vanish with the new socket's first partial — and the new socket's text is merged after it (`mergedTranscript` / `transcriptContinuation`), so a restatement replaces rather than doubles. The new socket never heard the outage, so a segment that had one is **always finished by the upload**: `finish()` closes the stream without waiting and hands over to the batch session. The trace records `streamReconnected`, and `DictationReplay`'s `.connectionDrops` step reopens a scripted socket through the same closure.
- **Spans, not one re-joined string** — `RecognitionEvent.live(committed:partial:)` keeps the two halves apart, and `TranscriptSpanLayer` is what they are kept apart *for*: the increment of the cumulative `committed` string becomes a span, and the commit adopts the id of the partial that was showing those words, so a sink that already drew the partial can replace it in place instead of appending a second copy. The engine no longer stores `liveText` — it feeds the layer and computes `liveText` from `spanLayer.segmentText`, which keeps the per-segment meaning the views have always had (a pause hands its segment over for insertion and the ghost text starts again) while the recording's whole timeline survives in `spanLayer.text`. States carry the rules: `settled` and `frozen` are terminal, so a segment result and a provider that restates its committed text both refuse to touch what the user edited by hand. A segment result equal to what the spans already spell settles them where they stand rather than redrawing them — the smallest version of "replace only what differs".
- **Tiers, from what the field proved it can do — now only for the Edit shortcut** — `DeliveryTier` (DeliveryTier.swift) answers one question: can the Accessibility API read *and* re-select the focused field's text? Tier A is our own surface, or a foreign app that proved both; Tier B is everything else (Chromium and Electron answer inconsistently for `contenteditable`, terminals never answer at all). The probe's load-bearing step is the read-back — `PasteService.probeFocusedText` writes the selected range the element already has and compares what comes back, because Chromium returns `.success` on that write and then reports a different range, and a probe that trusted return codes would file VS Code under "correctable". The decision is pure logic so it is testable without an app to focus: `PasteService` does the AX I/O and hands the answers in as an `AXTextProbe`. It used to be taken at the start of every inline recording, to decide what that recording could hand over while the user spoke; with nothing handed over before the stop a dictation never probes. `PasteService.readSelection` asks it when the Edit shortcut reads a selection: Tier A is read through AX, with the range `PasteService.select` re-selects before the cut, and everything else with a ⌘C.
- **A span is drawn, never issued** — spans used to be pasted into the target app as they committed, never a partial (a partial pasted into a foreign app could never be taken back), each at most once and in order, which `SpanIssuer` guaranteed by construction. Nothing is issued now: the overlay draws the committed spans at full brightness and the partial dimmer, and the stop pastes `spanLayer.text` once. `SpanIssuer` went with the path it served; the span layer's ids and states remain, because the overlay and the Record Window are both sinks that draw a partial and then replace it in place.
- **The ledger records the document's copy** — `InsertionLedger` (pure logic, in SpeechTextCore) is what a sink keeps: where a span landed and *what the sink actually holds there*. The sink's copy, not the string sent — a text view with substitutions on or an app that normalises line endings stores something slightly different, and a guard that compared against our version would refuse every correction it was asked to make. The Record Window's ✨ (through `FinalizePass.plan`) — and `TextInsertionHandler.replaceSpan`, the hook for hand edits, which nothing calls yet — replace text only where `resolve` can still find it: the recorded range if the text there matches, otherwise the one *unambiguous* occurrence elsewhere, otherwise nothing at all — two identical occurrences resolve to nothing, because "the last one" is a guess and a guess may not rewrite the user's document. The Edit shortcut builds a one-record ledger for the selection it read, so `PasteService.select` finds the words untouched before it re-selects them. The stop subtracts nothing any more: an inline dictation hands nothing over before its stop, so `remainder(of:)` — the guard against a third doubled dictation, with its tolerance for a batch fallback that re-worded the first word — went when the stop became the only paste, and so did the "Part of the dictation wasn't pasted" notice it fed.
- **One write at the stop** — the stop's paste is the only write an inline dictation makes. `InlineDelivery.stopResult` decides it from `spanLayer.text`, the whole recording, not `finalText`: a device restart leaves `finalText` holding only its last segment, and pasting that dropped what came before. Plain text is pasted; AI mode hands the same text to the LLM and pastes the rewrite (or, on any failure, the text as dictated); a failed transcription pastes nothing and hands whatever there is to the Record Window. There is nothing to correct first, so the hook that used to run a correction before `.idle` woke the stop (`SpeechEngine.onFinalize`) is gone, and History's `correctionApplied` with it. No backspace is ever simulated.
- **The paste goes where the dictation ended** — an inline dictation is pasted into the app in front when the user stops, whatever app it began in; a setting to paste where it started was proposed and rejected — one behaviour, one path. `AppState.stopRecording` fixes `pasteDestination` on its first line (`InlineDelivery.destination`), while the app the user stopped in is certainly the one in front — the overlay is a non-activating panel, so that is the user's app, not ours. Fixed at the stop, never re-read at the paste: an AI rewrite takes 1–12 s, the user may move again meanwhile, and `deliver` re-activates the app they stopped in — so the prompt's `<context>` and the destination are always the same app. Every step after the stop is handed the destination, not the origin: the paste, `focusContext` (and so the password-manager exclusion and History's `Refinement.context`), the Debug Log's `paste target: X (started in Y)`, `DictationTrace.Setup.destination`, and History's `destinationApp`. The *origin* is `dictationOrigin` (`InlineDelivery.origin`, the app in front at the start): the fallback when SpeechText's own window is in front at the stop, and what `deliver` uses when a stop never passed through `stopRecording`. A dictation started in SpeechText's own window has none, so one that also ends there goes to the Record Window — it used to go to `previousApp`, the app of whatever recording came before. A Try it dictation has no destination — its result belongs to the setup window. The Edit shortcut (the selection is its target by definition) and the Record Window (`pasteTextToTarget`, its Insert button) still paste into `previousApp`. **A ⌘V is posted only into the app in front**: every paste into another app — the stop's, the edit's rewrite and put-back, Insert — asks `InlineDelivery.pasteCheck` after the blind wait whether the app it re-activated is now the frontmost one, because the ⌘V goes to whichever app is, macOS 14's cooperative activation can be declined without `activate()` saying so, and an app that quit during a rewrite never comes back (`PasteService.activateApp` no longer asks AppleScript to activate one, which relaunched it). Being in front is not enough either: while a Control Center menu is open (Control Center itself, Sound, Wi-Fi, Bluetooth — `PasteService.openMenuBarMenu`, which reads Control Center's focused window) the app beneath is still `frontmostApplication` but the menu has the keyboard, the ⌘V is lost, and activating the app does not close it (measured 2026-10-22, after a dictation stopped with Bluetooth just switched off in Control Center was reported "Pasted into TextEdit" and pasted nothing) — `pasteCheck` answers `.menuOpen`. Otherwise nothing is pasted: a dictation goes to the Record Window with a notice, and History's destination is taken back (`recordNotPasted`), so the record says Record Window rather than the app it was meant for; an edit's text goes to the clipboard.
- **Dictations are replayed, not hosted** — the test bundle cannot host the app, so it cannot run `SpeechEngine` or `AppState`; what it can run is everything between the provider and the document. `DictationReplay` (SpeechTextTests) feeds scripted `StreamingSTTEvent`s into a real `StreamingRecognitionSession` (its fallback is typed by the protocol, so the batch answer is scripted too), the events through `TranscriptSpanLayer` — keeping every frame the overlay would have drawn — and the stop through `InlineDelivery.stopResult` into `FakeApp`, a document in memory — as many of them as the user switches between, the one pasted into chosen by `InlineDelivery.destination` exactly as the app chooses it. Every replay asserts that nothing reached any app before the stop. The engine and AppState glue between those pieces is repeated in `DictationReplay.run`, step by step with the source named, and its span-layer and stop half is `InlineDictationFlow` (SpeechTextTests/LiveDictation.swift), which the live corpus runs share; **a change to that order in `SpeechEngine.stopRecording` or `AppState.handleTranscriptionResult` has to be mirrored there**, or the replay and the corpus test a flow the app no longer has. What a replay cannot show is whether a real app takes the paste — that is the e2e harness's (`scripts/e2e.sh`, for the apps AppleScript can read back) and, beyond it, a pull request's *Needs a real-app run*. Real dictations become fixtures through `DictationTrace`: Debug Log › Record traces or `scripts/e2e.sh --traces`, `scripts/import-trace.sh` into the private traces folder, and `scripts/replay-traces.sh`, whose `RecordedTraceTests` replays them (the recorded pastes must recur, or a reviewed `expectedDocument` must). The traces stay out of the repository at the owner's call: even a corpus clip's words are not published as a recording.
- **A segment boundary is a space unless the provider cut a word** — Scribe's realtime VAD closes a segment on a moment's silence, and a stumble inside a word splits it ("…база дани" | "х, звідки", 17.09). `segmentSeparator` (TranscriptMerge.swift) glues a boundary only when the first segment ends in a letter, the next opens with a lowercase letter, the halves together are a word and the second half alone is not. A first segment that trails off into `...` / `…` straight after a letter is read past: Scribe ends a segment closed inside a word that way and opens the next with a capital ("перфо..." | "Ратор."), so `joinedSegments` judges that boundary on the letters before the dots and the next segment with its first letter lowercase, and when it glues, drops the dots and writes the second half in lowercase ("перфоратор."); a capital that continues no cut word keeps its case and its space ("нова... | Версія." — the model's capitals are not rewritten, at the owner's call). Dropping the dots rewrites text the stream reported before, which the span layer only sees as growth because `cleanedTranscript` drops a trailing `...` anyway; with cleanup off it redraws the segment once. Words are checked by `TranscriptJoin.isWord`, which `registerSpellCheckedJoins()` (SpellCheckedJoins.swift, in SpeechTextCore — apart from App.swift so the corpus runs register it too) points at `NSSpellChecker` at launch — the language follows the script, because the English checker accepts any Cyrillic word — and one-letter fragments are judged by `TranscriptJoin.oneLetterWords` instead, because a spell checker accepts every single letter. Unregistered it glues nothing. The decision is made once, in the streaming merge (`joinedSegments`), and carried from there: `TranscriptSpan.joinsPrevious` is read off the cumulative committed text, and the span layer joins its text by it — what the overlay draws and what the stop pastes alike. Run over all 300 History records (5,077 word boundaries treated as cuts) the rule glued one pair, an English "de | ne"; "Чи | я" was the other until "я" joined the one-letter list.
- **Clipboard restores coalesce across a burst, and yield to the user** — several pastes in quick succession (a recording that pasted each span as it committed, as it once did) broke the save/restore pair that protects the user's clipboard: the second paste's save read back the *first paste's text*, so a second later the user's clipboard held a fragment of their own dictation. `PasteService` takes the snapshot once per burst and cancels and reschedules the pending restore instead of stacking a second one behind it. The restore also compares the pasteboard's `changeCount` with the one recorded when our text went on: a ⌘C the user pressed mid-dictation changes it, and putting the old snapshot back over that copy would be the same bug from the other side.
- **⌘V, ⌘C and ⌘X are looked up in the layout, never hard-coded** — a virtual key code names a position, and 0x09 is V only on QWERTY: on Dvorak the paste did nothing and the Edit shortcut's ⌘X cut nothing, or something else. `PasteService.commandKeyCode(for:)` asks the current layout (`TISCopyCurrentKeyboardLayoutInputSource` + `UCKeyTranslate`) which key types the letter *with ⌘ held* — that is what makes Ukrainian and "Dvorak – QWERTY ⌘" answer with the QWERTY position — trying the ANSI position first and falling back to it. Not cached: it runs per paste and costs nothing. The shortcut is posted as a person types it — ⌘ down, the letter down and up, ⌘ up, 20 ms apart (`CommandKeystroke`, ShortcutConflicts.swift, in SpeechTextCore) — never as one letter whose flags merely say ⌘: Chrome 156 read the pasteboard for that and inserted nothing, so a dictation into a web page was reported pasted and left the field empty (measured 2026-11-01; ⌘ pressed around the letter, or the event posted at the HID tap, pasted). Everything we stage on the pasteboard also carries `org.nspasteboard.TransientType` / `AutoGeneratedType`, so clipboard managers do not archive each dictation (never `ConcealedType`, which some apps refuse to paste), and the process-wide AX messaging timeout is 1.5 s instead of the system's 6 s per call, so a hung app cannot hold a stop for half a minute. `IsSecureEventInputEnabled()` is only *logged* with each paste: it is not established that secure input blocks a posted ⌘V, so nothing is refused on it.
- **A silent segment is not uploaded** — Whisper answers silence with "Thank you for watching", which would be pasted. `AudioBufferWriter` tracks the peak of the converted samples and `BatchRecognitionSession.finish` returns an empty outcome — after writing the file, so it is still archived for a History retry — when it never reached `STTTuning.silencePeakFloor` (−44 dBFS: a muted or dead microphone, a shortcut pressed with nothing said; room noise above it still goes to the model). Native-fallback audio is unmeasured and counts as audible. History retry calls the provider directly and is not guarded against silence, but it does drop a known hallucination. The same guards apply to a **stream's** answer, which the server's model gives whatever the microphone heard — a shortcut pressed and let go pasted "Evet.": `StreamingRecognitionSession.guardedStreamResult` runs the duration and peak tests on the writer (skipped when it holds nothing — a replay) and `HallucinationFilter.rejection` on the text, with the user's stated languages for the script rule. A segment of up to `STTTuning.hallucinationSegmentSeconds` whose *whole* result is a known hallucination comes back empty from either tier, its audio archived for a retry, and while it is all a stream holds the overlay draws nothing — so the span layer only ever sees the real words extend an empty view. A segment shorter than `STTTuning.minimumSegmentSeconds` (0.3 s — a shortcut pressed and let go at once) goes further: it is dropped *before* the file is written, as `RecognitionOutcome.discarded` — no upload, no error, no History row (it is spelled `cancelled`, the one outcome `recordOutcome` records nothing for). Separately, `AudioBufferWriter` writes anything under one FLAC block (`flacBlockFrames`, 4 608 frames) as WAV: Core Audio's FLAC encoder turns such a recording into a 42-byte file with no header that nothing can open, so the writer never hands out an undecodable file, whoever asks for it.
- **A segment with no voice in it is not sent** — keyboard typing, a fan or the street are louder than the silence floor, and the engines answered them with «Thank you for watching.» or «so». After the silence guard, both sessions ask `VoiceActivity.read`: the upload tier before it uploads — nothing sent, nothing billed, the file archived as a silent segment's is — and the stream at `finish()`, where the audio has already gone up the socket but what came back is not pasted. History retry is not judged: the user asked for it. The rule is measured, not guessed, on the corpus's own tap path (`SpeechTextEvaluation`, which keeps each row's highest window and count — the file path FluidAudio resamples itself gave other numbers): a lone «Так.» filled exactly two 256 ms windows over 0.85, every longer recording of speech at least four and a whisper six, keyboard noise none, and room noise on a MacBook's microphone one isolated window (0.95) in fifteen seconds. So a segment needs two windows, and one when it lasts at most 2.5 s — a one-word dictation is short, and losing it is worse than letting a moment of noise reach the engine (the owner's choice, 2026-10-11). A cough is a voice to the model at any setting, which is why `HallucinationFilter` still judges what comes back.
- **Sessions, not provider branches; one per segment, the archive stays with the engine** — `makeRecognitionSession` is the only place that knows which tier a configuration selects, so `SpeechEngine` has no *per-segment* `if provider == …` recognition branches — the one remaining per-segment `provider == .apple` test, in `setupRecordingSession`, caches the `SFSpeechRecognizer` across sessions to keep the speech model loaded, which is exactly why it cannot live inside a per-segment session; it builds a fresh `RecognitionSession` for every segment (a resume is a new session), but the `AudioBufferWriter` and the History calls stay in `SpeechEngine`: the writer must exist for every tier (it is the batch upload, the stream's fallback *and* the archive kept when on-device recognition returns nothing), and the tap must be gone before it is dropped — `cleanup` tears the engine down before resetting the writer for exactly that reason. Sessions report; the engine records.
- **One phase enum, booleans are views over it** — the engine's state is the single stored `RecordingPhase`; `isRecording`/`isPaused`/`isTranscribing`/`isStartingEngine` are read-only computed properties. When these were four stored flags, a stop that set `isRecording = false` a line before it set `isTranscribing = true` could be observed in between as "idle" — a phase write is atomic. `@Observable` tracks the computed getters through the stored `phase`, so every view keeps updating without change. `awaitTranscription()`'s waiters resume from `phase`'s `didSet` on the `isTranscribing` true→false *edge*; `paused(segmentInFlight: true) → finishing` is deliberately not an edge, because a stop that arrives while a paused segment is still uploading is now waiting on that same segment. `segmentFinishStarted` stays a separate flag on purpose: "this segment's audio was already sent" is not a phase — it survives `paused(true) → paused(false)` and is what stops a stop-from-paused from uploading the same audio twice — or, after an Apple pause that wrote the segment's History row, from asking the session again and writing that row twice. `cleanup()` never writes `phase`; every caller but `cancelRecording` (which discards the result) sets `.idle` immediately before calling it, after its result fields are in place, so a resumed waiter always sees a finished result. The Debug Log shows one `phase: a → b` line per transition instead of three flag lines.
- **The socket opens before the microphone does** — `setupRecordingSession` calls `session.start()` (and so the realtime transcriber's `connect`) before `installAudioTap` and before the background `prepare()`/`start()`, so the TLS handshake overlaps the 100–300 ms the hardware takes. Audio the tap produces before the server's `session_started` is held in `ElevenLabsRealtimeTranscriber.preSessionMessages` — already encoded as socket messages, so the flush is only `task.send` calls and never stalls the audio thread (it runs under a separate `sendLock` that orders the socket's batches; holding the state `lock` across a send would deadlock against a synchronously-delivered send completion, whose `fail` → `close` path takes that same lock) — and released when it arrives, so the first syllable is neither dropped nor reordered behind later chunks; a `finish()` before the session started sends what was held ahead of the commit. `send` takes `sendLock` *before* it empties `pendingAudio` and holds it until the chunk is on the socket: released between the two, a `finish()` could win the lock in the gap, find nothing pending, commit only its padding, and the chunk would land after the commit in a segment that never closes — up to 100 ms of the last word. If the bound (`STTTuning.streamPreSessionBufferSeconds`) fills, the stream *fails* rather than dropping the oldest audio: a transcript missing its opening seconds must not be recorded as a success, and the batch fallback has the whole segment on disk. `finish()` likewise does not trust the first `committed_transcript` it sees — the server answers in order, so a VAD segment closed just before the stop lands first — and waits `STTTuning.streamCommitGraceSeconds` for a partial that would show the final segment is still coming. The partial that shows it, though, must be a *new* one: Scribe also re-sends a segment it has just committed as one more `partial_transcript`, and taken at face value that echo both joins the same words on twice (the dictation pasted doubled) and holds `finish()` for its whole timeout waiting on a segment that will never be committed — so `ElevenLabsRealtimeTranscriber.isEchoOfCommitted` drops a partial equal to the last committed text. The echo is not always equal: re-heard, it can come back with other words ("Все так, як ми домовились." → "Всі так раптом домовились, що вони...", 1.10), and nothing on the wire says which commit a transcript answers. So once `finish()` has sent its commit, `StreamFinishSettle` (pure, in SpeechTextCore; the replay's scripted provider settles a stop through it too) holds any partial that follows a commit reply instead of passing it on: a later commit carries its words, and one still held when the wait ends — an echo, or the final segment behind an earlier VAD segment's late reply with its own commit late or throttled — fails the stream, so the stop uploads the segment rather than guess between pasting it twice and dropping its tail. That equality is only the first frame of the echo, though: keep talking and the re-statement *grows*, arriving as the whole accumulated transcript with a word or two revised, which an equality test cannot see. So `StreamingRecognitionSession` does not join what the stream reports — it merges it (`TranscriptMerge.swift`): `mergedTranscript` replaces the committed text with a re-statement of all of it (the server's later version saw more audio) and `transcriptContinuation` reduces a partial to what it adds. Word-level comparison, punctuation-insensitive, with a `restatementAgreement` tolerance for the revised words and a `minimumRepeatedWords` floor below which a repeat is taken for speech rather than for a re-send.
- **The Dictionary's words reach the engine as a list, and Groq's as a prompt on trial** — a model is sent the user's words through a parameter that *is* a term list: OpenAI's `keywords` (upload `keywords[]`, the realtime session's `transcription.keywords`), Scribe's `keyterms` (repeated form field; repeated query parameter on the socket) and Apple's `contextualStrings`, each within its `TermListLimits`. Groq's Whisper takes free text instead, its `prompt` (`RecordingConfiguration.whisperPrompt`), which is sent at the owner's call (2026-10-01) to be tested: a Whisper prompt is reported to be echoed back on silence — which the hallucination filter cannot catch, since they are the user's own words — and a list of Latin-script terms may pull a Ukrainian dictation towards Latin script; the audio corpus measures both, each clip with a vocabulary run with and without it and the silence and noise clips carrying words too (docs/audio-corpus.md). WhisperKit's prompt tokens stay unsent, and Parakeet's vocabulary is English-only. One switch on the Dictionary page (`sendVocabularyToEngine`) sends nothing to any engine when off; the replacements still run. Two limits are ours, not the vendors': Scribe's upload takes 1000 terms but bills a request carrying more than 100 as at least 20 seconds, so it is sent 100; OpenAI states no count, so it is sent 100, unmeasured. The terms go in each provider's initialiser, so the stream's reconnect closure and its upload fallback carry them without asking, and a History retry reads them fresh with the rest of the settings. No terms, no field: a request without a vocabulary is byte for byte what it was. The Debug Log records the count, never the terms, which are often names.
- **Hesitations are cleaned before they become spans** — `no_verbatim=true` is echoed back by the server and Scribe still writes Ukrainian "е-е-е", so `SpeechEngine` runs `configuration.cleaned` on every `.live` event, on Apple's `pause()` text and on each `RecognitionOutcome`, and History retry does the same. Not at the stop: the overlay draws the spans while the user speaks, and the layer turns only the *increment* of the cumulative committed text into a span, so cleaned text that stopped extending what came before would be redrawn as a revision. That is also why `cleanedTranscript` must be monotone on whole-word extensions — a rule may rewrite a word only from that word and what came before, never edit a word already written (a filler's full stop is dropped rather than moved onto the previous word). History therefore stores the cleaned text as `record.text`: cleanup counts as transcription quality, and "raw" in the Refinement sense means "before the LLM".
- **Scribe quality flags are sent explicitly** — the upload API's `tag_audio_events` defaults to *true*, which would paste "(laughs)" into a document, so `ElevenLabsTranscriber` sends it off; `no_verbatim=true` goes on both the upload and the realtime query string (fillers and false starts dropped server-side; documented for scribe_v2). The batch model IDs in ElevenLabs' catalogue entries are exactly what the API's `unsupported_model` error lists (`scribe_v2`, now that `scribe_v1` is deprecated and `scribe_v1_experimental` gone); the realtime ID exists only behind the WebSocket.
- **`.task` captures the view by value** — which is why `PixelWaveform` reads levels through a small `LevelFeed` class rather than its own stored property, and why the task is keyed on `mode`.
- **Two signatures, and the one that survives a team change is ours** — an update is trusted twice over: Apple's Developer ID makes the app openable, and an EdDSA key that belongs to this project makes the *download* ours. They are deliberately independent. The Apple team ID is part of the identity macOS keys every permission grant to, and signing under another team (a transfer to a different account — converting this one to an organization keeps its team ID, docs/releasing.md) changes it — with a key of our own, the update still installs and only the permission prompts come back. `scripts/make-appcast.sh` signs each release and writes the feed; `scripts/package-release.sh` refuses to build a distributable image whose `Info.plist` has no `SUPublicEDKey`, because an app that cannot be updated looks fine right up until the next release cannot reach anyone. The feed carries one item, the release being cut: Sparkle installs the best item it finds, so a release needs nothing from the one before it.
- **Four dependencies, one file each** — WhisperKit, FluidAudio, Sparkle and llama.cpp are the project's only third-party code, a decision recorded in ROADMAP.md: Whisper needs a tokenizer and a decode loop that Core ML does not supply (and whisper.cpp publishes no macOS binaries to run as a sidecar), Parakeet needs a TDT decode loop and a mel frontend it does not supply either, and an app distributed outside the App Store needs a downloader, a signature check and an installer able to replace a running app. Everything around each of them is Foundation — for the two speech engines the catalogue, the hardware read, the recommendation, download bookkeeping, the provider shape and the Settings UI; for Sparkle the menu item, the settings rows and the packaging. `import WhisperKit` appears only in `LocalWhisperRuntime.swift`, `import FluidAudio` only in `LocalParakeetRuntime.swift` and `VoiceActivityRuntime.swift` (the Parakeet engine and the voice activity detector — the same package, so no fourth dependency, at the owner's call), `import Sparkle` only in `UpdateChecker.swift`, and `import llama` only in `LocalLlamaRuntime.swift`, which the app does not compile: llama.cpp runs in the SpeechTextLLM service, so a crash or a model that exhausts memory ends the service rather than the dictation, and AI Rewrite pastes the transcript as for any failed rewrite. llama.cpp came in (2026-10-16) so AI Rewrite on this Mac would need nothing else installed; MLX was passed over because swift-transformers does not resolve beside WhisperKit, and llama.cpp has no package graph at all — ggml-org's prebuilt xcframework, pinned by build (`Packages/LlamaBinary/`), whose daily prerelease builds are moved deliberately, with the rewrite evaluation rerun. That is what keeps the standalone test bundle building, and it makes replacing any of them one file per use. For SpeechTextCore the rule is enforced by its manifest, which declares no dependency: an engine's import there is a build error, not a finding for review. The `SpeechTextEvaluation` tool links WhisperKit and FluidAudio too, compiling the same runtime files; it ships nothing. FluidAudio also pulls a prebuilt Rust `NemoTextProcessing.xcframework` for text normalisation we never call; it is a static `.a`, so it links into the binary and adds nothing to sign or embed. Since 0.18 it also embeds `FluidAudio_LuxTtsG2pResources.bundle` (1.0 MB, measured 2026-11-07), the pronunciation data of a text-to-speech model we never call: espeak-ng output under GPL-3.0-or-later and word lists under CC-BY-SA-4.0, both listed in `ThirdPartyNotices.txt`.
- **Registration, not imports, for the local tier** — `Transcribers.swift` is in SpeechTextCore, which links neither WhisperKit nor FluidAudio and cannot see the app, so its `makeBatchTranscriber` switch cannot name `WhisperKitLocalTranscriber` or `ParakeetLocalTranscriber`. It calls `LocalSTT.transcriberFactory`, which `registerLocalSTT()` (LocalSTTRuntime.swift) points at the real engines at launch, dispatching on the catalogue entry's `LocalSTTEngine`. The unregistered default throws `LocalModelError.notInstalled` rather than returning "" — an empty success would skip the failure paths that keep the audio for a History retry. Two engines behind one `STTProviderType.local` is deliberate: "a model on my Mac" is one choice to the user, and a second provider case would have doubled the recognition tier, the History archive, retry and onboarding to describe a difference they never make.
- **The local tier is a batch tier** — `.local` goes through `BatchRecognitionSession` like Groq, so the engine, the History archive and retry need no new branches, and that holds for both engines. Retry asks `RecordingConfiguration.batchUnavailableReason()` instead of testing a key: the local tier needs an installed model, and "add a Groq key" would be the wrong advice. FluidAudio does ship a sliding-window streaming manager, so a live local preview is possible later; it is deliberately not wired up, because `makeStreamingTranscriber` is keyed off the cloud engines and the confirmed/volatile split would have to be mapped onto the span layer.
- **Load once, decode one at a time** — the expensive part of local Whisper is loading, not decoding: a Core ML model's first load on a Mac specialises it for the Neural Engine — 45 s for Small and **9 minutes** for Turbo on an M1 Pro. `LocalModelStore` shows that as its own `InstallState.optimizing` ("installed" while nothing seemed to happen was the alternative); the model is `isUsable` meanwhile, and a dictation simply waits for the same load. `WhisperKitPipelineCache` keeps one pipeline resident, `LocalModelStore` prewarms right after install so that cost lands in Settings rather than in front of the first paste — and `LocalSTT.prewarm` loads the selected model again at launch (`prewarmSelectedLocalModel`), when Settings picks one and when a dictation starts, because Core ML's compiled copy (`~/Library/Caches/<bundle id>/com.apple.e5rt.e5bundlecache`, per macOS build and per model file) does not outlive a macOS update, a cache purge or the model's files being replaced: Parakeet v3 loaded in 28.9 s without it and 0.2 s with it (M1 Pro, 2026-10-16), and the first dictation after such a launch waited that long before its paste. Prewarming one engine's model unloads the other engine's — the prewarm after an install too, which then gives way to the selected model if the user did not take the new one — so only one local model is ever resident, and removing a model unloads it only if it is the one loaded (`LocalSTT.releaseModel(modelID)`), and jobs are chained because an actor re-enters at every `await` and a pause followed quickly by a stop can finish two segments at once. `WhisperKit` is not `Sendable`, so the pipeline never leaves the actor. Parakeet's first loads in a process, measured on an M1 Pro (2026-10-16): v3 29 s, Ultra 25 s, Phonon-2 103 s, Redux on the GPU under a second. That cache belongs to the process's bundle identifier, so the app pays its own first load even after `SpeechTextEvaluation` loaded the same files.
- **The tokenizer lives in the model folder** — it is not part of the Core ML download; WhisperKit fetches it on first load and by default writes it to `~/Documents/huggingface`, which raises the macOS Documents-folder prompt and leaves it outside anything Remove deletes. `tokenizerFolder` is set to the model folder (one of WhisperKit's own search paths), so the post-install prewarm fetches it once, while online, next to the model.
- **Model storage and the rename migration** — models live in `Application Support/SpeechText/Models/`, inside the folder `adoptPreRenameStore()` moves wholesale. That migration only runs when `SpeechText/` does not exist yet, so `LocalModelStore.install` touches `TranscriptionHistory.shared` before creating anything, and `SystemCapabilities` measures free space on the Application Support *root* rather than creating `SpeechText/` to ask.
- **Tiers pick two models, and candidates step down** — `MacTier` (by memory) selects a `TierPicks`: *recommended* is the fastest model of good enough quality, because the user is waiting on the paste; *best quality* is the strongest the tier can hold. Each is a candidate list, and `firstFitting` takes the first that clears its RAM floor and fits on disk, so a Mac at the bottom of its tier (24 GB in the 24–32 GB tier, 96 GB in the 96–128 GB tier) or with a nearly full disk steps down instead of overfilling. Speech excludes the large models on Intel (no Neural Engine — a hardware fact, not a memory shortage, and it rules out Parakeet for the same reason); chat does not, because llama.cpp runs on Metal — but an Intel Mac is offered the small model first and warned that a rewrite runs on its processor alone. Speech does not scale with the Mac at all — every Apple Silicon tier gets Parakeet v3 for both picks, so a Mac Studio with 512 GB transcribes with the same model a 16 GB MacBook Air does, only faster — and chat stops at Qwen3.8 27B for now: larger GGUF models are for later. **The 8–32 GB picks are measured** (2026-09-17, M1 Pro 32 GB, Ollama 0.34.1, six dictations through the app's own prompt and parser): Qwen3.5 2B failed (Ukrainian turned Russian), 4B was usable with misroutes, Qwen3.5 9B and Gemma 4 12B handled all six at 2–4 s with Gemma cleaner — so Gemma 4 12B leads 16–32 GB — and Qwen3.8 27B wrote the best text at 5–14 s, hence *best quality* only. On speech, Whisper Small and Base answered Ukrainian in Russian spelling (38–100% WER) while English was perfect, and the full Large v3 reproduced Turbo's errors word for word ~30% slower — so no tier is steered to it. **Parakeet v3 was measured on 2026-09-21** against a real 12.4 s Ukrainian dictation — not `say -v Lesya`, which every engine transcribes near-perfectly and which therefore discriminates nothing: it returned the same text as ElevenLabs Scribe v2, where cloud Whisper Large v3 Turbo (the same weights as the local Turbo variant, unquantised) misread the first word, and it answered in 0.34–0.61 s from a cold process against Turbo's nine-minute first-load specialisation on this Mac. At 483 MB to Turbo's 645 MB there is no tier where Turbo fits and it does not, so it leads all of them. The caveat is honest: that is one sentence of real speech, and a longer dictation is the confirmation. **Ultra, Redux and Phonon-2 were run through the audio corpus on 2026-10-16** (M1 Pro, Auto and uk+en passes): on Ukrainian, mean WER v3 0.180 / Ultra 0.177 / Redux 0.226, median 0.050 / 0.056 / 0.124, stop to text 0.25 / 0.28 / 0.97 s at the median; on English all four tie where no Ukrainian is spoken; Phonon-2 answers Ukrainian with nothing usable (WER ≥ 0.9 on every clip). The rerun for FluidAudio 0.18.2 (2026-11-07, 50 clips, Auto pass, on the same model files) matched 0.17.7 everywhere except that the `<unk>` markers 0.17.7 left in nine cells are gone. The owner kept v3 as the recommended model and the default (2026-10-17) and asked for picks that follow the Mac and the person: since #5's stage 2, someone who speaks English alone on macOS 15+ is recommended Phonon-2, a disk v3 no longer fits on steps down to Redux before Whisper Small, and a language Parakeet does not know (Arabic, Chinese, Hebrew, Hindi, Indonesian, Japanese, Korean, Malay, Norwegian, Thai, Turkish, Vietnamese among the app's list) gets Whisper Turbo. Bark 3.0 and Bark 3.0 Clean (#43) are offered on macOS 15+ and picked for nobody: on the corpus (M1 Pro, 2026-10-26, and again on FluidAudio 0.18.2 on 2026-11-07) Bark 3.0 had Phonon-2's WER on every English clip and Clean too but for the fillers it drops by design, both loaded first in 95–98 s as Phonon-2 does, and Clean pasted a word for a cough on the MacBook microphone on every pass, so the English-alone pick stays Phonon-2. The 36 GB+ picks are **not** measured (no such hardware); Gemma 4 26B leads the pro tier as the MoE sibling of the 16–32 GB winner.
- **AI Rewrite on this Mac is read once and restored** (2026-10-16) — the rewrite prompt's system part is the same on every dictation (it is built that way), and reading its ~880 tokens is most of a local rewrite's wait: six seconds for Gemma 4 12B on an M1 Pro. The service saves the model's state after it and restores that state for every request, so only the transcript is read; and an AI dictation or an edit asks the service to load the model and read the system prompts the moment it starts (`LLMConfiguration.prewarmIfLocal`), while the user speaks: the one for an editor, a program in a terminal or an AI's field first, since most dictations go there, then the routing prompt for every other field, then the Edit shortcut's. A terminal's two prompts for a shell are not read ahead, so the model is not made to read five on a Mac that never dictates into a terminal: the first dictation there reads its prompt, 3.5 s against 0.5 s restored on Gemma 4 12B (M1 Pro, 2026-11-08). Five are kept (`LlamaModel.savedPrefixes`), one per prompt a request can be sent; at three the prewarm pushed the shell's out before every dictation. A state is about 147 MB, held once its prompt has been used. Measured through the real service: a cold request took 14 s, a prewarmed one 1.3–2.9 s. A stored Ollama pick moves to the built-in path at launch (`migrateOllamaPick`): the same model where the catalogue has it, downloaded again, since Ollama's store is not a GGUF file of ours; a remote Ollama has no replacement.
- **Small models write the mode marker loosely, and large ones abbreviate its name** — Qwen3.5 2B/4B/9B emitted `<<Email>>`, `<mode:Translate>…</mode:Translate>` and `<<mode:Clean-up>` instead of `<<mode:NAME>>`, and the strict parser left those in the pasted text. `TextRefinementService.parse(_:presetNames:)` also takes a loose first-line marker (and a trailing closing tag naming the same preset — a reply's own `</div>` stays), but only when the name is exactly one of the presets, ignoring case — a reply that genuinely begins with `<div>` stays untouched. The strict marker is closed only by a `>>` right after its name: searched for anywhere, a `>>` later in the body (a shell redirect) closed `<<mode:Clean-up>` and everything before it was lost. The *name* inside a well-formed marker gets the same test (`canonicalPresetName`): gpt-oss-120b writes `<<mode:Technical>>` for `Technical / Prompt` (measured 2026-09-22 on two of three such dictations), and a name matching no preset is dropped rather than written to `Refinement.presetName` — that field exists so a routing choice which looks wrong can be traced back to a preset, and a preset the user does not have traces to nothing. The marker still comes off the text whatever it names; only the name can be lost. A loose form is looked for only when there was no strict marker at all, since running one over a body a real marker already came off would cut text the model meant to keep.
- **Cloud catalogues are checked against the vendor, not remembered** — last on 2026-09-16. Groq shut Llama 3.3 70B (the old default), Llama 3.1 8B, Qwen3 32B and Kimi K2 down for free and developer accounts, so Groq's chat catalogue is gpt-oss 120B/20B plus two labelled previews; those models were deleted from the catalogue before models had a lifecycle, so a stored ID for one is now cleared at launch (and the default pinned for whoever has Groq in use). Groq's reasoning switches differ per family and the wrong one is an HTTP 400: gpt-oss takes `reasoning_effort: low` + `include_reasoning: false` and rejects `reasoning_format`; Qwen takes `reasoning_effort: none` + `reasoning_format: hidden` (its default `raw` puts `<think>` into the content); `OpenAICompatibleChatClient` also runs `strippingReasoning` for a model that documents no switch. ElevenLabs deprecated `scribe_v1` and dropped `scribe_v1_experimental`, so ElevenLabs' default (its `ModelSetting` in `ProviderDescriptor`) is `scribe_v2` — the default, the realtime stream's fallback and History retries alike. The Anthropic and OpenAI defaults are the fast end that still rewrites well (Sonnet 5.5 and GPT-6 Luna since 2026-11-01, when Claude 5 and Haiku 4.5, the GPT-5.6 family and GPT-6 Sol were superseded by their successors — the Settings pickers list such models last, folded under *Legacy models*, `modelPickerRuns`); Fable 5.1 and GPT-6 Astra are left out as slow and expensive for a clean-up. `strippingReasoning` is the fallback for a model that reasons inline anyway, where it would push `<<mode:NAME>>` off the first line.
- **Carbon Events API** — Global hotkeys use `RegisterEventHotKey` / `InstallEventHandler` from Carbon.HIToolbox (the only way to register system-wide hotkeys on macOS).
- **No app sandbox** — Disabled in entitlements to allow accessibility APIs (`AXIsProcessTrusted`, the AX reads of other apps) and the synthetic keystrokes the paste and the Edit shortcut's cut post as `CGEvent`s; the global hotkeys are Carbon's and need neither — there is no event tap.
- **Bluetooth headphones are left to play** — a Bluetooth headset whose microphone opens drops to its call profile: music goes mono and muffled, and the microphone takes about a second to open, which can cost the first words. So the microphone choice (`SettingsKeys.microphone`, Settings › Dictation › Microphone; macOS's own Dictation names its equivalent *Microphone source* in System Settings › Keyboard; *Automatic* and *System Default* are ours) defaults to **Automatic**: the system's input, except that a Bluetooth one is replaced by the Mac's own microphone — only that, never an iPhone or a virtual device, and not with the lid closed, when it is disconnected in hardware though still listed. *System Default* is the behaviour from before the setting; a picked device is pinned even when the default moves, and one not connected falls back to Automatic. The choice is snapshotted in `RecordingConfiguration`, but the device is resolved by `SpeechEngine.makeCapture` each time a capture is built — a start, a resume, a restart after a device change — so a headset that leaves mid-recording falls back on its own. A resolution with no device keeps `AVAudioEngine` on the system's input (`EngineCapture`, the old path); one that names a device is captured from that device alone through a bare AUHAL (`DeviceCapture`), never through `AVAudioEngine`: touching its `inputNode` builds `CADefaultDeviceAggregate` from the system's input and output and binds the I/O unit to it, so with Bluetooth headphones it opened the headset's microphone — the call profile, the music gone for seconds — before `setDeviceID` moved it to the Mac's microphone, and the tap was left on the headset's 48 kHz against the microphone's 44.1 kHz, failing the start with -10868 (measured in the system log on 2026-10-06). A device that cannot be opened is logged and the system's input used. The first substitution shows a notice once (`microphoneNoticeShown`) with Change, which opens Settings › Dictation.
- **A device change keeps the segment** — `.AVAudioEngineConfigurationChange` under a live recording rebuilds only the `AVAudioEngine` and its tap (`restartAudioEngine`): the `AudioBufferWriter` is re-prepared for the new hardware format and keeps appending to the same 16 kHz buffer, and the cloud/local `RecognitionSession` never sees a boundary. Rebuilding the whole session, as this used to, replaced the writer before its audio was written and cancelled a batch session whose `cancel()` is a no-op — the first half of a Groq or local dictation vanished, with no History row, when AirPods connected mid-sentence. Apple's request takes native buffers, whose format just changed, so that tier (and a writer already on its native fallback path) goes through an ordinary pause and resume instead — the resume waiting, for a segment that has to be uploaded, until its transcription has landed (`pauseRecording(thenResume:)`): `resumeRecording` cancels the segment's task, and with it the upload, so it refuses `.paused(segmentInFlight: true)` outright, and the Record Window's shortcut, like its knob, ignores a press while the engine is busy. A change that leaves the capture running is ignored: pointing `AVAudioEngine` at a device with `setDeviceID`, as the app did before `DeviceCapture`, raised one of its own about 40 ms after the start, and treating it as a device change tore down the starting engine — the dictation sat in `.starting` recording nothing — or restarted a recording engine, whose new selection raised the next, until the budget ended it; a capture that stopped during `.starting` is restarted rather than torn down, for the same reason. `DeviceCapture` marks itself stopped before it reports a change, as `AVAudioEngine` does. More than five changes in ten seconds (`deviceRestartBudget`) — a headset that will not settle, where each restart raises the next notification — end the recording with what was said instead of looping. A change while *paused* only discards the stale engine: the resume builds a fresh one anyway, and going idle left the Record Window showing a pause the engine had abandoned. Engine `prepare()`/`start()` and every `stop()` run on one serial `engineQueue`, because a cancel that stopped the engine on main while a start was mid-flight on a background queue mutated one `AVAudioEngine` from two threads. The stop is queued asynchronously (waiting would stall main for a slow Bluetooth start) except before a restart's re-`prepare` of the writer — so the stop's task may write the file while a tap callback is still inside `AudioBufferWriter.append`, which is why `append` converts under the lock the flush takes; a start's success block moves the phase only from `.starting`, so a pause or stop that landed during a restart is not overwritten by `.recording`. An Apple pause writes its segment's History row as the batch tier does, and a stop from that pause finishes from it rather than writing it again.
- **A start that fails says so** — `SpeechEngine.onStartFailure` fires (before `.idle`) when the session cannot open or the engine will not start; `AppState` takes the overlay down and shows a status notice — except during setup's Try it, which is handed the failure (`DictationTest`) and explains it in its own panel. Nothing else reads `errorMessage` until a stop, and a failed start never reaches one, so the "preparing" overlay used to sit on screen until the next hotkey press. A start the microphone has not answered in 8 s (`SpeechEngine.startDeadline`) is a start failure too, and the next start gets a fresh `engineQueue`; and a dropped `AVAudioEngine` is deallocated on a queue of its own (`EngineCapture.releaseQueue`), because its dealloc waits on its I/O unit's queue, which a property listener re-reading a vanished device held for good (2026-10-29) — released on `engineQueue`, it left every later dictation "starting" forever. `startRecording` also ignores any phase but `.idle`: a start during `.starting` rebuilt the session under itself, and one during `.finishing` cancelled the stop's result. **A recogniser that fails before any text ends the recording too** (Apple's on-device task failed 44 ms in with "Failed to access assets", and the overlay listened for 12 s until the user stopped). A task that reports an error is over, so `RecognitionFailure.endsRecording` is set whenever the session holds no text yet — whatever the error — and `SpeechEngine.endRecording(after:)` acts by phase: in `.starting` (the Apple task opens before the audio engine) it is a start failure, `onStartFailure` and no History row, since no audio was taken; in `.recording` it is the ordinary `stopRecording()` — `finish()` returns the error at once, History keeps the row — followed by `onRecognitionFailure`, which the inline flow answers with the rest of a stop (`waitForTranscription`, so the result is the usual "Transcription failed" notice) and the Edit shortcut by ending the edit once that row is written; the Record Window sets neither and just shows `errorMessage` with its knob back at idle. A failure *after* text leaves the recording running, as it always did: the text is kept for the stop, and the session opens a fresh task at once instead of at the next 50 s rotation (`AppleErrorRotation`, in AppleRecognitionSession.swift). Nor does it make the dictation a failure: while the segment has words neither the event nor the outcome's error reaches `errorMessage` (`recordOutcome`; text that cleanup empties is no words), so the stop pastes them — an error left there sent them to the Record Window under "Transcription failed", as the "No speech detected" a chunk that heard nothing after a rotation can answer the stop's `endAudio()` with would. The words between a mid-chunk error and the next rotation used to be lost, with no notice — up to 50 s of them; now the gap is the fresh task's start, at most a second for a chunk that heard words (the e2e `apple-error` scenario fails one on cue), and the 50 s timer only once three fresh tasks in a row died without a word. A failure's clip under `STTTuning.minimumSegmentSeconds` is not archived (no provider could retry it), but its History row stays. The notice says what the error does: kLSRErrorDomain 102 names the language whose speech model macOS could not load and points to Dictation in System Settings › Keyboard; kLSRErrorDomain 201 ("Siri and Dictation are disabled" — a new macOS account's state, which `isAvailable` does not reveal) says Dictation is off and where to turn it on; Speech Recognition denied or restricted (`SFSpeechRecognizer.authorizationStatus()`, read, not inferred) is refused at `start()` with its own remedy; anything else keeps the recogniser's words. The wording is `RecognitionFailure.apple`, pure and in SpeechTextCore, and must fit the notice's two lines, which `RecognitionFailureTests` measures as laid out. The History row stores that explained message; the raw error stays in the Debug Log. **A microphone that goes away ends the recording as a stop** — no usable input after a device change, a restart's engine that will not start (its catch in `startAudioEngine` used to go idle and reset the writer: the dictation gone, no row), or more than `deviceRestartBudget` changes (`endRecording(microphoneLost:)`): the ordinary `stopRecording()`, History keeping the row, then `onMicrophoneLost`, which the inline flow answers with the rest of a stop in `stopRecording`'s order (`handleMicrophoneLost`: the destination fixed from the app in front then, the focus context in AI mode, `waitForTranscription`), so what was said is pasted once; the Edit shortcut ends the edit as for a recognition failure, and the Record Window, which sets neither, is handed the stop's text as a pause's segment. Before, the row was written and nothing pasted, the overlay stayed up, and the next press — the stop still transcribing — cancelled it. The reason is kept out of `errorMessage`, where it made a result with words a failure handed to the Record Window: it explains only a segment that comes back with no words and no error of its own, whose row and notice then say why the dictation ended (`DictationReplay`'s `.microphoneLost` step mirrors it).
- **Settings are snapshotted per session** — `SpeechEngine.startRecording` reads a `RecordingConfiguration.current(locale:)` once and every later step (pause, resume, stop, the stream fallback, the device-change restart) uses that copy; only `locale` is updated, by `resumeRecording(locale:)`. Before this, each step re-read UserDefaults, so changing the engine picker while the mic was live could send the second half of a recording to a different provider than the first. Two consequences are deliberate: provider, model and API key are frozen at start, and the batch upload's `language` is the segment's `cloudLanguage` captured at start/resume rather than `resolvedLocale()` re-read at stop (the Apple path already worked that way). History retry is the exception — it reads a fresh configuration, because a retry exists to try the settings the user has *now*.
- **Stored-value normalization** — `normalizeStoredProviders()` (Settings.swift) runs at launch and from the Settings view: a `sttProvider`/`llmProvider` string that no longer maps to a case is reset, and every stored model ID goes through the model lifecycle: one the vendor is retiring (`deprecated`, or in the archive) is moved to *its own* replacement, chains followed — never to the provider's default, which may be another kind of model — and the move is recorded in `modelMigrations` for the next dictation's notice; one that leads to no offered model (deleted before lifecycles existed, or hand-edited) is cleared to `clearedModelChoice` (an empty string, which pinning leaves alone — an absent key would read through to the default and be pinned) for the user to pick: until they do, a dictation on that engine is refused with a notice naming the model and opening the picker, and AI Rewrite pastes the text as dictated (`LLMError.noModelChosen`), at the owner's call (2026-10-17). A model is never deleted from a catalogue to retire it: History prices records from the current table, so a deleted ID would turn them "Not priced". Users move with our release, at the first launch of the version that marks the model; the shutdown date is shown, never a trigger. It also deletes the keys of features that were removed (`webhookURL`, `authToken`, `aiFocusContextEnabled`), so nothing stale lingers in the domain.
- **A default nobody stored is still a setting** — an absent model key reads through to the provider's default, so moving a default would move every install that never picked. So every launch pins it: `pinUntouchedModelChoices` writes the default down for the speech engine and AI provider *in use* — not every provider's, or a Groq user would get today's local default in `localSTTModel` and, once it moved, a model they never downloaded — and the old default is then marked `.superseded(by:)` so the switch is offered; only new installs get the new default. Pinning protects only installs that launched a release with it before the default moved. The local tier is pinned only to a model on disk, whichever engine is in use. Before pinning existed, nothing wrote `localSTTModel` until the user opened the model picker: `@AppStorage` and `RecordingConfiguration.current()` both read through to the local provider's default (`Provider.local.defaultSpeechModel`). So moving that default is not the harmless edit it looks like — when it went from Whisper Turbo to Parakeet, every install running the local tier on the old default would have been pointed at a model it had never downloaded, and the next dictation would have failed with "Parakeet v3 isn't installed". `preserveInstalledLocalModel()` (Settings.swift) closes it: an absent key plus a model on disk is written down as the user's choice — the old default first, then today's default, else the heaviest installed. A fresh install has nothing on disk and falls through to the new default, which is the point of moving it. Any future change to that default has to go past that function.
- **Rename migrations are opt-in per key** — `SettingsKeys.portable` is an allow-list rather than a copy of the whole old domain, because a blanket copy would also bring the `didAdoptPreRenameDefaults` marker itself, marking the migration done before it ran, along with `hasRegisteredLaunchAtLogin` (see the rename paragraph at the top, which also covers the API keys). A new setting that should survive a rename has to be added to `portable`.
- **One-time shortcut migration** — `AppDelegate.migrateHotkeyLayoutIfNeeded()` clears stored hotkey values once (guarded by `hotkeyLayoutVersion`) so a changed built-in layout reaches existing installs; later customisations survive because the version has already been bumped.
- **The Dictionary corrects final text, never live text** — `RecordingConfiguration.finished` (= `cleaned`, then `Vocabulary.corrected` — the Dictionary's spellings and the Replacements table — then the dashes again) runs on every segment *result* (`SpeechEngine`'s pause and stop, Apple's pause, `HistoryRetry`), and the result replaces the live spans through `commitSegment`, so the stop pastes, AI Rewrite reads and History keeps the corrected text. It is not applied to the `.live` events as `cleaned` is: a spelling of two words ("speech text" → "SpeechText") would rewrite a word already drawn on the overlay, which the span layer would have to draw as a revision. The engine is told the Dictionary's words as **The Dictionary's words reach the engine as a list** describes; the page says what the engine in use gets. The Dictionary is the one store: Settings › Speech › Vocabulary (`customVocabulary`), built in parallel, was folded into it on 2026-10-01 and its list moved over at launch. Every LLM reply — AI Rewrite's and, at the owner's call (2026-10-01), the Edit shortcut's, whose selection is the user's own text — goes through the same corrections (`TextRefinementService.polishedReply`), so a model cannot write a wrong spelling back. `DictationReplay` applies `finished` to the segment result as the engine does. AI Rewrite gets a `<vocabulary>` block in the user message (data, like `<context>`), described by one line of each system prompt's hard rules (`vocabularyRule`), and the Edit shortcut's user message carries the same block (`editUserMessage(…vocabulary:)`), so a selection's names are kept as written.
- **A language is forced only when the user names exactly one** — "Languages I speak" (`spokenLanguages`) is a list, and the count decides everything. One language: it is sent to every engine, which is the accuracy win the setting exists for. Two or more: `cloudLanguage` is nil and the model detects, because **almost no provider API accepts a set** — checked 2026-09-21, Groq's `language`, ElevenLabs' `language_code` (upload and realtime), OpenAI's upload `language` and WhisperKit's `options.language` are all single values, and `SFSpeechRecognizer` takes one locale with no detect mode at all. **The one exception is `gpt-live-transcribe`**, OpenAI's realtime model, whose session config takes `languages: ["en", "fr"]` — an actual candidate set, which is why one language sent in the singular form comes back from the server normalised to `languages: ["uk"]`. That is the one place the user's whole list is worth more than its first entry, so `StreamingTranscriber.connect(languages:)` takes the list rather than a resolved language and each provider honours what its API allows: `encodeSessionUpdate` sends the set, Scribe's query string sends `language_code` only for a single language, and everything else treats two or more as none. `RecordingConfiguration.languages` carries the list beside `cloudLanguage`, which stays the *forced* answer. Picking one of several to send would be the keyboard-layout guess wearing a different hat, which is the bug below. The cost of detection is that a cloud model judges the language segment by segment, so a Ukrainian dictation can come back in Russian after a pause (seen 2026-09-17, with no language stated); naming exactly one is the remedy. What several languages *do* buy is Apple's guess: `resolveLocale` lets the keyboard layout choose only *among* the stated languages, so a Russian layout no longer selects Russian for someone who never listed it, and with no match the first stated language beats a layout the user never claimed. None stated keeps the pre-list behaviour exactly. The list is stored ahead of the one tier that could honour it properly: WhisperKit's `detectLanguage` returns `langProbs` over every language, so a local dictation could take the argmax *within* the set — deliberately not built yet, since the local tier's UI has not been exercised in a real build.
- **Auto language detection is Apple's problem, not the cloud's** — With no single language named, `resolvedLocale()` reads the active keyboard input source and maps it to a locale, because `SFSpeechRecognizer` must be handed one. A cloud provider is handed *nothing*: `RecordingConfiguration.cloudLanguage` is nil on Auto, and Whisper and Scribe detect the language from the audio. Forcing the layout's guess on them was a data-loss bug, not a mis-spelling — dictating Ukrainian with a US layout sent `language_code=en`, and Scribe answered with a two-second English *translation* of an eleven-second recording (History's own records: every truncated or transliterated entry carried `locale=en`, and 70 of 91 `en` records held Cyrillic text). History records `historyLocale` — "auto" when the model chose — so a record never claims a language that was never requested, and a retry takes the language from the current settings rather than repeating the guess.
- **The focus context is data, and the system prompt always describes it** — window titles and field labels are written by other people (an email subject, a web page's title), so the context goes in the *user* message as a `<context>` block with angle brackets defused, and the system prompt says it is a hint for the form of the output that the transcript always overrides and that nothing inside it is an instruction. That system-prompt section is always included, even for a dictation that has no context (the Record Window, a password manager): the system prompt stays identical from one recording to the next. An AI dictation reads it in `stopRecording` from `pasteDestination`, after the engine has been asked to stop — the app the text is going to, so a letter written for Mail cannot land in Slack, and a password manager in front at the stop sends nothing whatever app the dictation began in. An edit reads it at its start from the app in front, after the engine has been asked to start: its AX round trips to a slow app would otherwise delay the tap. The Debug Log records the app but not the window title, since every entry also goes to the system log as public. History keeps it on `Refinement.context`, so a preset choice that looks wrong can be traced to where the model thought the text was going.
- **A command at a shell prompt** (the owner's call, 2026-11-08) — AI Rewrite writes a shell command only where a shell is listening. In an editor, an AI's field or a program in a terminal an instruction stays the user's words, since "list every file bigger than…" in Claude Code is a request to Claude Code; at a prompt it becomes `find . -size +100M`. This replaces the spec's D3 for shells: D3 cited an owner's decision that was about language, and the behaviour it removed was what every model did unprompted. `TerminalFocus` reads which it is, without a new permission: Terminal's title ends with the job (read from the end, because a program or a remote host can write the rest), and the process table gives each tab's foreground. Every tab at a shell is a shell wherever the cursor is; ssh and tmux hide what is behind them; several tabs with only some at a prompt leave the title, which cmux keeps to the directory at a prompt and only there is trusted. Where nothing says which, the words stay unless the user names a command. A reply that may be a command reaches the paste on one line (`RewriteModes.forPaste`): at a shell, a reply of two lines is dropped for the transcript, since joining them would make another command. Dictionary and Replacements are not applied to it, and a terminal's title is not sent, so a reply cannot run itself and a remote host cannot suggest one; nothing presses Return. Measured on Terminal and cmux, and on the six engines ×3 over the eight terminal fixtures, as pasted: 136 of 144. Every model wrote the command at a prompt and left a remark as words; of the misses, GPT-OSS 20B wrote a command unasked behind ssh (3), a model took a Dictionary word into a path (3), Haiku explained itself (1), and one wrote «МБ» for «мегабайт» (2026-11-08).
- **An edit cuts the selection when the instruction ends, and puts it back on any failure** — while the user speaks the instruction the selection stays where it is (reading it changes nothing). The moment the instruction is over (the second press, the release, a double press) it is cut with ⌘X, so nothing the user does while the LLM works can make the rewrite land on the wrong text: the caret is where the selection was, and the rewrite is a plain paste there. Softer ways for the text to go were tried on 19.09 and removed at the user's call as not worth their complexity: a violet shimmer laid over the selection in a window of our own (did not look right), and erasing it word by word with AX-selected ⌫ steps (worked in TextEdit; Chromium applies AX selections late and reports an emptied field as its placeholder, and every workaround added another failure path). What is cut is **the selection when the instruction ends**, not the one read at the first press: `takeSelection` reads it again (`PasteService.readSelection`, unless the first read itself landed after the instruction ended) and `SelectionEdit.target` decides — the same text, other text (the user selected something else while speaking, and the text they can see selected is the one they mean), nothing selected ("No text selected", nothing edited) or too long. The first read stays: it stops an edit with nothing selected at the first press. Neither the second read nor the cut happens unless the app the edit began in is still in front (`SelectionEdit.takesSelection`): both are keys posted to whichever app is, and the rewrite is pasted into the one it began in, so after a ⌘Tab while speaking — which the hold tip says works — the edit ends with "The selection was in another app" and neither app's text is touched. The cut is checked before it counts: in Tier A `PasteService.select` first finds the recorded words untouched (`InsertionLedger.resolve`) and re-selects them, and in every tier what the ⌘X took must be the text that was read — markup and whitespace aside, since T3 Code's composer reports its Markdown rendered through AX and copies the source, which is then what the LLM is given (`SelectionEdit.cutMatches` / `cutSource`) — anything else is pasted straight back and the edit stops. The ⌘X keeps every pasteboard type the app wrote, so a cancel, an instruction that could not be transcribed, an LLM failure or a rewrite that changes nothing pastes the *original* back, formatting included (`putBack`). Never through `kAXSelectedTextAttribute`: T3 Code (Electron) accepts that write with success and ignores it. A field where ⌘X changes nothing (read-only) keeps its text and the rewrite goes to the clipboard. "Changes nothing" is decided after 600 ms (`PasteService.awaitChange`), but the pasteboard is watched 3 s longer (`watchForLateChange`, ended by any write of ours): a ⌘C that lands late has the user's clipboard put back, and a ⌘X whose text is the selection has it too, its cut pasted back where it was if the app is still in front, else left on the clipboard with a notice — whatever the edit has done meanwhile, since it took the field for read-only. The rewrite itself is plain text, so formatting inside a selection that *was* rewritten does not survive. No edit cancel is silent: every user cancel (⎋, ✕, a dictation or Record Window shortcut, the Edit shortcut while the AI works, a lone tap, a menu item) carries an `EditCancelReason` and `cancelEdit` shows "Edit canceled", saying the text was put back when it had been cut. A dictation shortcut pressed during an edit cancels it (its recording is an instruction, and a mode switch would paste it), and the Edit shortcut is ignored while a dictation runs. History stores the edit as a `Refinement` with `editsSelection`: `inputText` is the selection, the record's `text` the instruction (empty with none). An instruction that came back empty is not written to History on its own (`SpeechEngine.recordsEmptyOutcomes` is off for an edit): it is the same as a double press.
- **Preset routing in one call** — The LLM both picks the mode and applies it in a single request; it reports its choice on a leading `<<mode:NAME>>` line that `TextRefinementService.parse` strips. This avoids a separate router round-trip while the user waits for the paste (a two-step router is #110's measurement, docs/specs/2026-11-03-rewrite-modes-and-router.md). The prompt is `RewriteModes` (#109): three built-in modes, each a kind of text — Clean-up, Message and Structured — and the user's own prompts beside them; language, format, length, tone and "write it better" are rules applied on top of whichever mode was picked, not modes, because a spoken request stacks them ("a letter in English, keep it short") and a mode per modifier made the model drop one. "Output only", "invent nothing" and the clean-up are said once, for every mode. **In an editor, a terminal or an AI's prompt box the dictation is text for that program**, so code, not the model, decides it (`FocusContext.Kind`): Clean-up alone, sent with a prompt that has no marker and no modifiers, unless the user has prompts of their own, which are offered there beside Clean-up. Before, one rule asked the model to tell "rewrite this file in English" dictated into Cursor from the same words in Slack, and the context rule beside it said an editor meant code — they contradicted each other, and the model sometimes carried the instruction out. A built-in is known by its fixed ID, so a renamed or edited one keeps its place. Measured before it shipped (2026-11-04/05, 73 fixtures × 3, docs/rewrite-evaluation.md): each of the four engines measured passed more text checks than with the six presets of October 2026 — Sonnet 5.5 195 → 214 of 219, Haiku 5.5 206 → 212, GPT-6 Luna 196 → 210, Gemma 4 12B 198 → 201 — and each did better in code fields, though Gemma still turned "list every file bigger than…" in Terminal into an `ls` pipeline, and Luna and Gemma translated a Ukrainian instruction dictated into Cursor; the October prompt stays in the harness as its baseline (`buildSystemPrompt` over `PromptPresetStore.october2026`). The whole prompt goes out on every AI dictation, and a free tier's allowance is per minute, so its length is a budget: framing 1900 and the three modes 1250 characters (`testTheRoutingPromptStaysWithinItsBudget`; 3102 in all, against 3615), the Clean-up-only prompt 1500. Prompt *length* is not a latency driver — 5204 and 1139 characters were measured at the same half-second — so the budget is about rate limits. Only the primary mode is reported, so History's counts under-report a language or a list that rode along. The prompts a user saved before move once at launch (`PromptPresetStore.migrateIfNeeded`, `promptPresetsVersion`): a built-in left as it shipped, in either text git holds for it, becomes the new one or goes (Rewrite / Draft, Translate, Technical / Prompt); one the user edited stays as they left it, as their own.
- **No connection says where the dictation is** — with no network the stream fails, the upload fails and the audio is archived, which used to end in "Transcription failed" with the URLSession error. The batch session now marks such an outcome `offline` (`NetworkFailure.isOffline`, from the typed error, never from its message), the engine keeps the failed row's id in `offlineRecordID` — apart from `lastRecordID`, which the LLM pass and `recordApps` attach to — and `AppState` shows "No connection — saved to History" with a **Retry** button (`StatusOverlayAction`) instead. A retry's result stays in History, with a notice whose Show opens it there — never into the app in front, where by the time it lands the user may be typing anywhere, and never onto the clipboard, where it replaced whatever the user had copied meanwhile and a later ⌘V pasted a dictation from minutes before (the owner's call, 2026-10-22; it used to go there). A retry that finds no network again shows the same notice. Without a click the dictation is retried by itself once the network is back (`OfflineRetry`) — only what *this* session saved, since a recording archived last week is History's to retry at the user's word — and the whole outage gets one notice, "N dictations not pasted", counting failures too (a timeout, a file too large), which used to drop out of the queue unsaid. Such a record is marked `TranscriptionRecord.undelivered` by `recordFailure(offline:)` — the Record Window's too — and the inline flow fills in the app in front at the stop, whether it was an AI dictation, and the `FocusContext` read for it (`recordUndelivered`, keyed on `offlineRecordID`, never `recordApps`, which must not name a failed row). The mark is never cleared: `HomeRecentEntry.place` answers *Not pasted* for it before any fallback — a retry's rewrite records a context naming the app, which would otherwise read as where it went — and the row carries a "For Slack" tag (`Tag.notPasted`) and says it was not pasted. `HistoryRetry` rewrites a record whose mark says AI (`retryRewrites`), after `markRetrySucceeded` cleared the old pass, told the stored context; a rewrite that fails keeps the transcription, as at a stop.
- **Graceful LLM degradation** — Every LLM failure path (missing key, HTTP error, refusal, empty response, a reply cut off by its token budget or the context) falls back to the raw transcription rather than producing nothing, surfaces a status overlay, and is written to the history entry so a silently-unrewritten paste is explainable after the fact.
- **Attaching the LLM pass to a history entry** — `SpeechEngine` writes the history record, but refinement happens later in `AppState`/`DirectRecordingPanelView`. The engine exposes `lastRecordID` (cleared on each new session) so the LLM step can update that entry instead of creating a second one. A successful retry clears any refinement, since it described text that no longer exists.
- **The app's language is the system's per-app setting, and says nothing about speech** — Setup and Settings › General write `AppleLanguages` to the app's own preferences (`AppLanguage`), the key macOS's own per-app language control writes, so the two cannot disagree. Foundation reads it at launch and `uiLocale` is fixed for the process, so a change restarts the app (`AppInstaller.restart`, which opens the new process only after this one has gone, so it never finds the shortcuts still held). `Locale.current` takes its language from that key, so `resolvedLocale` reads the system's `AppleLocale` instead: Ukrainian windows on an English Mac must not change the language assumed for dictation.

## First run

A new install opens the setup window instead of asking for the microphone and Accessibility in two unexplained alerts at launch (`AppDelegate.decideSetupGate`). An install that predates setup — a login item already registered, any `portable` setting stored, or an API key held by `APIKeyStore` (`hasAnyKey`) — is marked done and never shown it. That evidence is read right after `adoptPreRenameDefaults()` and `openAPIKeyStore()` and **before** the other launch migrations, because they write portable settings on a new install too (`migrateSelectedLanguageIfNeeded` always stores `spokenLanguages`): read after them, every new install passed for an old one, and setup never opened. A `.show` stores `onboardingCompleted = false` at once, so the settings setup's own steps write cannot make the next launch take an unfinished setup for an old install. Its Permissions step continues only once the microphone and Accessibility are allowed — there is no skip, since a dictation that cannot be typed is not one — and, with Apple Dictation chosen, macOS Dictation is on (`OnboardingModel.permissionsComplete`). While setup is showing, the launch does not register the login item; the Permissions step turns it on (default ON, as before) next to the switch that turns it off. An app opened from the disk image moves itself to Applications first (`AppInstaller`); the image is left for the user to eject. Setup writes each step's choice on its Continue — the languages on Welcome excepted, written as they change: the speech engine explicitly (the Apple default knows no Ukrainian, so Apple Dictation is offered on the Speech step as one row of *On this Mac* — `OnboardingModel.speechUsesApple`, never a model ID, so Continue installs nothing — rather than taken by default; ElevenLabs gets `scribe_v2_realtime`, since the card promises live words), the AI provider only if one was chosen ("Skip for now" writes nothing). Closed half-way, it opens again at the next launch on the step it was left on; the status menu offers "Continue Setup…" only while it is unfinished — once done, everything it asks is in Settings, so it is not offered again. Its Try it step runs the real shortcuts and the real overlay, but `AppState` hands the result to `DictationTest` instead of pasting — the app never pastes into its own windows — and ignores the shortcuts while the chosen local model is still downloading or being prepared. It offers Settings' `RecordingModePicker` (Hold to talk / Press to toggle — `holdFirst`, `compact`) at the top of the step before the first dictation — setup stores `holdToTalk = true` when nothing is stored, so a new install starts on Hold to talk while an install that never saw setup keeps the app's `false`; what to say stays on screen while the shortcut is down (a short email to Josh; for AI polish, a sentence with hesitations to tidy); once that worked and AI polish is set up, it offers the AI shortcut on the left at the same size, and an AI dictation's panel holds only what was said and what the AI wrote — what was said cut to one line once the AI has written, with Show all, and the panel grows to 18 lines as far as the window allows. The step's mode picker stays in place, dimmed, while a dictation runs, and its states cross-fade (`stageKey`) — a column that grew and shrank at each press and release flickered. With Apple Dictation chosen, the Permissions step adds a Dictation row: macOS Dictation on or off, read from `Dictation Enabled` in `com.apple.assistant.support` (absent — a new account — reads as off), with Open Keyboard Settings and nothing more, since the row has to fit — the recogniser fails with kLSRErrorDomain 201 while it is off. A failure — a start failure included, which raises no corner notice during setup — is told in the step, with a button to the System Settings page its message names (Keyboard for Dictation, Privacy for Speech Recognition), and Try again (`DictationTest.reset`, or `resetRewrite` for an AI one, keeping the plain dictation that worked). Done's Start using SpeechText opens the main window (`OnboardingWindow.finishAndOpenApp`). While setup is unfinished, Home opens with *Finish setting up SpeechText* (`HomeAttention`: the engine, the microphone and Accessibility with ✓ or not, Continue Setup and Skip — which marks setup done, since everything it asks is in Settings); once it is done, Home says when the microphone or Accessibility is missing, with Turn On…, re-read every second (`HomeAccess`). Try it's AI dictation routes as every AI dictation does — a sentence naming a meeting and a person may come back as an email, and that is kept at the owner's call. With Press to toggle, while the keys that started a dictation are still down the step says they can be let go. The Permissions step re-reads every permission each second while shown, since turning one off in System Settings never brings setup to the front. Welcome's demo takes turns between holding the shortcut and pressing it. The one way past Try it without finishing it — waiting for a download, a dictation or the AI — is *Skip test and finish setup*, always at the foot of the right panel, and the time a model takes to get ready is said the same way there and in the download pill (`preparationEstimate`). `ModifierKeys`, which draws the live keycaps, adds its global flagsChanged monitor only once Accessibility is allowed: asked for without it, macOS raises its "would like to control this computer" alert each time a keycap view appeared.

## Permissions

- **Microphone** — For audio capture (`AVAudioEngine`), from the device the microphone choice resolves to. Setup's Permissions step asks for it; on a launch that shows no setup, `requestMicrophoneAccess` runs from `applicationDidFinishLaunching`.
- **Speech Recognition** — For Apple on-device STT (`SFSpeechRecognizer`). There is no explicit `requestAuthorization` call: the system raises the prompt the first time an Apple segment starts a recognition task, so a user who only ever runs a cloud engine is never asked for a permission the app would not use. `NSSpeechRecognitionUsageDescription` is in Info.plist for that prompt. Once it has been denied, an Apple start is refused with a notice that says where to turn it back on.
- **Accessibility** — For simulating `Cmd+V` paste via CGEvent. Must be granted in System Settings > Privacy & Security > Accessibility. macOS's own "would like to control this computer" alert (`AXIsProcessTrustedWithOptions` with the prompt) is never raised, at the owner's call: it sat on top of the pane the helper already explains. `SystemSettingsGuide.accessibility` (OnboardingWindow.swift) is the one way to the grant — setup's Permissions step, Home, Settings › Privacy & Data and a notice's Turn On… — opening the pane with the helper and polling for the grant; `registerQuietly()` makes an Accessibility read that is refused, on the assumption (to be confirmed on a new account) that it lists SpeechText in the pane, switched off, without the alert. The grant is revocable and is attached to the app's code signature, so a rebuild or an OS update can silently drop it: Home says so (`HomeAttention`), and a dictation that could not be pasted says so with Turn On…, rather than an alert at every launch.
- **Automation** (`NSAppleEventsUsageDescription`) — Only for `PasteService.activateApp`'s fallback, when `NSRunningApplication.activate` fails to bring the target app back: an AppleScript `activate` sent to that app. macOS asks per target app the first time it runs.
